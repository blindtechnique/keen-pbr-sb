# FUZZ-01: Go-парсеры transport-manager

Цели запускаются локально или отдельным ограниченным CI-заданием. Они не
подключаются к роутеру, не запускают sing-box, не изменяют маршрутизацию,
не устанавливают пакеты и не скачивают подписки. Нужен Go 1.22 или новее.

## Что проверяется

| Цель | Вход и проверяемый контракт |
| --- | --- |
| `FuzzShareLink` | Поддерживаемые VPN/proxy URI, повреждённые порты, IPv6, query и credentials. Схема нечувствительна к регистру; параметры подключения — чувствительны. Принятый результат имеет endpoint и сериализуется без потери метаданных. |
| `FuzzBase64Payload` | Четыре варианта base64, padding и некорректные байты; VMess JSON и старые SS payload. Смена алфавита/паддинга не меняет параметры подключения. |
| `FuzzTransportConfig` | Link, outbound JSON и TransportSpec → чистые isolated/shared конфиги. Проверяются одинаковое принятие одного транспорта, детерминированность, отсутствие мутации spec, привязка к своему TUN и `auto_route: false`. |
| `FuzzTransportInput` | Существующие Go-декодеры одиночного и batch API после разбора подписки. Проверяются единственный JSON, round-trip, число узлов, display_name и граница чтения тела. |

Весь файл URI/base64-подписки разбирается **в C++**, в
`src/config/subscription_import_plan.cpp`; Go получает отдельные ссылки и
пакет TransportSpec. Здесь не добавлен второй парсер файла подписки и не
заявлено покрытие его C++-декодирования. Пять существующих направлений
`make fuzz` (C++/libFuzzer) не заменены и не продублированы.

## Запуск

Из корня репозитория, в Linux или окружении с Bash:

```sh
make transport-manager-test
make transport-manager-fuzz

# Один target, одна минута мутаций, не прогон остальных unit-тестов:
GO_FUZZ_TARGET=FuzzShareLink GO_FUZZ_TIME=60s make transport-manager-fuzz

# Короткий воспроизводимый бюджет по числу запусков:
GO_FUZZ_TIME=100x make transport-manager-fuzz
```

Без Make/Bash, в том числе в PowerShell, из `extensions/transport-manager`:

```sh
go test ./internal/transport -run '^$' -fuzz '^FuzzShareLink$' -fuzztime 60s -fuzzminimizetime 5s -parallel 2 -timeout 3m
go test ./internal/api -run '^$' -fuzz '^FuzzTransportInput$' -fuzztime 60s -fuzzminimizetime 5s -parallel 2 -timeout 3m
```

Обычный `go test ./...` воспроизводит seed corpus и сохранённые регрессии,
но **не выполняет случайные мутации**. Для них необходим `-fuzz`.
Runner отдельно проверяет наличие каждого имени: пустой выбор не считается
успешным fuzz-прогоном. При panic/ошибке/тайм-ауте возвращается ненулевой код.

## Ресурсные границы и ограничения доказательства

- Runner по умолчанию: 30 секунд мутаций на каждую из четырёх целей,
  два workers, тайм-аут 3 минуты на цель, минимизация ошибки до 5 секунд.
  CI ограничен 10 минутами на всё задание. Для длинной кампании необходимо
  явно увеличить и `GO_FUZZ_TIME`, и `GO_FUZZ_TIMEOUT`.
- `GOMEMLIMIT=256MiB` — мягкий Go GC-бюджет **на процесс**, не жёсткая
  гарантия RSS. Координатор и workers — разные процессы. Для жёсткого
  ограничения локальный запуск можно поместить в Docker с `--network none
  --cpus 2 --memory 1g --memory-swap 1g --pids-limit 128`; OOM/тайм-аут —
  провал, не пропущенный тест. Это тестовые параметры, не лимит роутера.
- Мутации share-link/конфига ограничены 64 КиБ, payload — 32 КиБ; API —
  4 МиБ + 1 байт. Это пределы генератора. Прежние **производственные**
  ограничения не уменьшены: подписка 1 МиБ/512 узлов, одиночный Go API
  64 КиБ, batch-обёртка 4 МиБ.
- Отдельные регрессии проверяют ровно 64 КиБ/4 МиБ и превышение на байт,
  0/1/512/513 узлов, длинную ссылку до 1 МиБ, много query-полей/ALPN,
  недопустимую глубину JSON и некорректный последний байт большого base64.
  Успешные результаты имеют линейную границу размера; декодеры API читают
  не больше своего лимита + 1 байт.
- Нет `recover`, который скрывал бы panic. Fuzzing не доказывает отсутствие
  всех дефектов, строгую линейность CPU/памяти или совместимость с реальным
  sing-box/провайдером. Физическая нагрузка на Keenetic — отдельный LOAD-01.

## Corpus и секреты

Начальные входы заданы в `_fuzz_test.go` и содержат только синтетические
`*.example`, `example-password`, тестовые UUID и документационные IP.
**Не использовать** настоящие подписки, конфиги, HAR, логи и бэкапы роутера.
Go сохраняет минимизированный сбой в `internal/<package>/testdata/fuzz/`;
прежде чем добавлять его в git, проверить содержимое. Расширяемый локальный
corpus runner хранит в игнорируемом `build/go-fuzz-cache`. CI не использует
общий cache; при провале сохраняет только минимизированные synthetic inputs
на 7 дней. Ошибки assertions не печатают исходные credentials.

## Исправления, найденные начальным corpus

1. VMess/SS принимали только нижний или полностью верхний регистр схемы,
   хотя dispatcher принимал и смешанный. Удаление префикса теперь одинаково
   для всех вариантов, payload не переводится в нижний регистр.
2. Outbound JSON принимал массив/объект/число/пробелы в `type`. Теперь
   требуется непустая строка. Не введён whitelist протоколов: расширенный
   outbound по-прежнему допускает новые строковые типы sing-box.
3. У старого формата VLESS сводка подключения теряла порт: в spec это
   `uint16`, а сводка знала только `int`/`float64`. Добавлено чтение `uint16`
   и проверки 1/443/65535; конфигурация и состояние туннеля не изменяются.

Случайные байтовые мутации также выявили неверное исходное свойство самого
теста: JSON штатно заменяет повреждённый UTF-8 на U+FFFD. Проверка теперь
сравнивает эквивалентные JSON-значения, а не исходные байты с нормализованной
строкой. Минимальный синтетический пример оставлен в corpus; новая
производственная блокировка из-за этой находки не вводилась.

Это локальные правки парсеров и тесты. Они не являются новой сборкой IPK,
не поставлены на роутер и не подтверждают готовность к выпуску.
