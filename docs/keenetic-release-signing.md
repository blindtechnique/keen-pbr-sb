# Keenetic release signatures

## Scope and trust anchor

The fork `blindtechnique/keen-pbr-sb` uses its own RSA-3072/SHA-256 key with
PKCS#1 v1.5 signatures. It does not reuse the upstream Debian/OpenWrt keys.
The implementation uses standard [OpenSSL dgst](https://docs.openssl.org/1.1.1/man1/dgst/)
sign/verify operations. There is no additional resident daemon or admission
check for routing, tunnel editing, subscription imports or Save/Apply.

Public key: `packages/keys/keenetic-release-public.pem`.
SHA256 of DER SubjectPublicKeyInfo:

```text
b2046fc89857f6d7ea4a58a1acf1dc4f5d9de4e0df5070475b1a90119f24632c
```

Full and headless IPKs carry `/opt/etc/keen-pbr/keys/release-public.pem` and
`/opt/usr/lib/keen-pbr/release-verify.sh`, and depend on Entware `openssl-util`.
No private key is shipped in Git, the WebUI, an IPK, a release asset or a log.

## Signed files

Releases contain full architecture-specific IPKs, compatibility `SHA256SUMS`,
the exact `install.sh` from the frozen source, `release-manifest.tsv` and its
binary `release-manifest.sig`.

The bounded ASCII/LF TSV manifest binds repository, channel, release identifier,
full source SHA and unique build identifier. File rows bind kind, architecture,
ABI, package version, SHA256 and basename. There is one installer and at most one
full package per architecture/ABI. Unexpected fields, duplicate targets, paths
and mismatched context are rejected. `SHA256SUMS` alone is not authenticity.

`build_scripts/sign-keenetic-release.py` signs and verifies the result against the
checked-in public key before exposing the output assets. Offline tests generate
separate temporary test-only keys; they never require the production secret.

## Verification and first adoption

1. Installed `self-update.sh` resolves one stable tag and downloads its manifest,
   signature and installer assets.
2. The already installed verifier/key authenticate that installer before shell
   execution. A public key downloaded alongside an update is never trusted.
3. The authenticated installer keeps the same release tag and verifies the
   architecture-specific IPK before unpacking helpers, staging rescue data or
   installing the package.
4. The existing transaction/restart path applies the update. Signature checking
   adds no service restart and does not restart nfqws.

The standalone installer embeds the same verifier and public key, generated by
`build_scripts/embed-release-verifier.py`; CI checks them against canonical
sources. On first installation only, missing OpenSSL is installed from the
configured Entware feed. Existing signed updaters require their packaged
dependency and do not bootstrap a new remote verifier.

**The first key cannot authenticate its own initial delivery.** A user-approved,
independently obtained bootstrap IPK/installer establishes the trust anchor.
The pre-signing updater is not retroactively authenticated. Plan the first
signed stable release and bootstrap delivery together: old unsigned releases
do not satisfy the new updater. There is no silent unsigned fallback.

Automatic updates remain stable-only. Alpha/next workflow artifacts and Beta
prereleases are signed but are not added to automatic discovery. Before manually installing
one, verify its IPK using the matching signed manifest/channel/release context.
Direct `opkg install` does not invoke our updater: this change does not claim
that opkg or third-party feeds independently verify this fork's manifest.

## CI and private key

Pushing `beta` builds all three supported Keenetic profiles: `aarch64-3.10`,
`mips-3.4` and `mipsel-3.4`. After the frontend, transport-manager, backend,
crash, thread-safety and firewall checks succeed, CI validates all three IPKs
against the frozen source, signs the bundle, uploads `keen-pbr-beta-ipk` and
publishes `beta-<run-id>-<attempt>` as a GitHub prerelease, never as Latest.
This tag is also the signed manifest's release identifier. To repeat a Beta
build, rerun its workflow or dispatch on the `beta` branch with an empty
`release_tag`; generated alpha/beta/next tags cannot enter the stable publisher.
Beta publication does not install anything on a router.

Actions secret: `KEENETIC_RELEASE_SIGNING_KEY`, PKCS#8 PEM inside GitHub Secrets.
[GitHub CLI encrypts values before upload](https://cli.github.com/manual/gh_secret_set).
Provisioning passes private material through stdin, never command-line arguments
or console output.

Only trusted stable/alpha/beta/next jobs in this fork sign artifacts. PR builds/tests
do not receive or require the secret. The key is scoped to the signing step;
its restricted runner temporary file is removed on success and failure. Missing
or mismatched keys stop publication before any existing release asset changes.

Signing tools come from the reviewed workflow commit; installer/packages come
from the frozen build source. Historical tags whose installer predates the
embedded verifier cannot be silently signed: backport a compatible installer
first. An authenticated installer must not then accept an unsigned package.

## Backup, rollback and key replacement

`build_scripts/provision-keenetic-signing-key.ps1` provides Inspect, Create,
Verify and Upload operations on Windows PowerShell 7. It creates a dedicated
RSA key, saves only a CurrentUser-DPAPI-encrypted PKCS#8 backup outside Git,
verifies recovery in memory and derives the public key. Upload does not replace
an existing secret without separate operator action.

Current backup: `%LOCALAPPDATA%/keen-pbr-sb/release-signing/v1/`, restricted to
the current Windows user and SYSTEM. **DPAPI needs this Windows account/profile;
copying the encrypted file alone to another PC is not a portable backup.**
Preserve the profile/recovery material or arrange a separate password-encrypted
offline export before replacing/reinstalling this PC. Never put a recovery
password in chat, Git or beside an unencrypted private key.

Stored local rescue snapshots remain usable offline, including pre-signing
snapshots. This change does not delete legacy rescue data, require a current
remote manifest during rollback or label legacy snapshots signature-verified.

Normal key rotation requires delivering the next trust anchor through an already
trusted release before switching signers. If the old key is lost or compromised,
use an independently authenticated bootstrap. Never automatically trust a
replacement public key fetched with a failed update.

## Acceptance boundary

80 focused offline checks cover real BusyBox verification/update ordering,
package contents and
workflow signing-step failures/key cleanup without production secrets or release
publication. They are not a real GitHub signing run or on-router proof.
Commit/push, an approved IPK build/bootstrap and a signed update on Keenetic are
still required before promoting the feature as deployed.
