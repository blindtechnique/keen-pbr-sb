# `list:set`: результаты исследования и границы внедрения

## Решение

**Автоматическое объединение наборов в рабочий firewall пока не включено.**
Оно уменьшает число строк, но не гарантирует ускорения. На небольшом числе
наборов дополнительная вложенная проверка может оказаться дороже. Следующий
шаг перед реализацией — измерения на поддерживаемом Keenetic, а не перенос
порогов с настольного Linux.

Речь только об объединении условий «адрес находится хотя бы в одном из
этих наборов» внутри **одного логического правила и одного семейства IP**.
Нельзя объединять правила просто потому, что у них одинаковый VPN: это
может изменить приоритет, условия, исключения или поведение при отказе.

`list:set` хранит ссылки на существующие наборы, а не объединённую копию
адресов. Проверка проходит по дочерним наборам до первого совпадения. Это
упорядоченное объединение, а не один новый hash-поиск. Команда `ipset test`
для такого набора проверяет наличие **имени дочернего набора**, а не IP;
проверку IP нужно проводить настоящим match пакета.
Источник: [официальное руководство ipset, раздел list:set](https://ipset.netfilter.org/ipset.man.html).

## Что уже делает сервис

- `firewall_runtime.cpp` создаёт отдельные наборы статических адресов и
  адресов, полученных из DNS, для каждого семейства. В одном правиле может
  использоваться несколько таких наборов.
- `IptablesFirewall::build_rule_lines` для обычного MARK формирует
  MARK/RETURN в RAW, а в mangle при сохранении conntrack —
  MARK/CONNMARK-save/RETURN. Общие условия повторяются на каждой строке.
- Наборы и элементы уже применяются через пакетный `ipset restore`.
  `list:set` не устраняет несуществующие отдельные fork/exec на каждый IP.
- Режим RulesOnly сохраняет наборы, а статические и динамические наборы
  имеют разные правила владения и времени жизни. DNS продолжает обновлять
  дочерние динамические наборы; переписывать dnsmasq на родительский нельзя.

## Воспроизводимый локальный стенд

Скрипт: [measure_list_set.py](../tests/firewall_it/scripts/measure_list_set.py).
Он запускается **только в одноразовом Docker-контейнере с отдельной сетью**,
не на роутере. Входящие/исходящие внешние подключения отсутствуют; используются
loopback и синтетические адреса `198.18.1.0/24`, `2001:db8:1::/64`.

Пример запуска с уже собранным образом из
[firewall_it](../tests/firewall_it/README.md), путь к исходникам заменить своим:

```sh
docker run --rm --network none --cap-add NET_ADMIN \
  --cpus 2 --memory 512m --entrypoint python3 \
  --mount type=bind,src=/absolute/path/to/repo/tests/firewall_it/scripts,dst=/lab,readonly \
  keen-pbr-firewall-it:iptables /lab/measure_list_set.py \
  --execute-in-disposable-container --backend legacy --table raw --families 4
```

Варианты: `--table mangle`, `--backend nft-compat`, `--families 4 6`,
`--semantics-only`. `nft-compat` означает **iptables-nft с xt_set**, а не
нативный `NftablesFirewall` проекта. Никакого автоматического переключения
между backend скрипт не делает. Отсутствие таблицы/модуля завершает проверку
ошибкой, а не превращается в успешный пропуск.

Классификатор написан для эксперимента вручную по ограниченной форме
production-правил. Выполняются настоящие kernel match, MARK, RETURN,
CONNMARK и UDP-пакеты, но **не** daemon apply, RCI, маршрутизация между
интерфейсами или полная транзакция сервиса. Измерение производится в OUTPUT,
не через LAN/PREROUTING роутера. Поэтому это исследование стоимости match,
а не end-to-end приёмка.

Локальная среда 15.09.2026: x86_64, Linux
`6.18.33.2-microsoft-standard-WSL2`, ipset 7.19 (protocol 7),
iptables 1.8.10, Python 3.12.3. Пройдены IPv4 legacy и IPv4/IPv6 nft-compat,
RAW и mangle. IPv6 legacy mangle в этой VM отсутствует; IPv6 legacy не
считается проверенным. Из этого ничего не следует о доступности модулей
в конкретной прошивке Keenetic с ядром 3.4/3.10.

## Результат: меньше строк не всегда значит быстрее

Для каждого сочетания — 5 чередующихся пар flat/union по 8192 пакета,
прогрев 128 пакетов, контроль фактического прироста счётчиков. Один дочерний
набор содержит один адрес; проверяются первое, последнее совпадение и промах.
Приведено изменение медианного времени локальной отправки/приёма пакета,
**отрицательное значение — быстрее**. Измерение включает Python и socket
overhead; это не процент ускорения интернета или VPN.

Основной локальный ориентир: IPv4 **legacy, RAW**:

| Дочерних наборов | Строк классификатора: flat → union | Первое совпадение | Последнее | Промах |
|---:|---:|---:|---:|---:|
| 1 | 2 → 2 | +7,4% | +8,8% | +4,3% |
| 4 | 8 → 2 | +4,7% | −0,2% | +2,3% |
| 16 | 32 → 2 | +5,1% | −9,5% | −8,6% |
| 64 | 128 → 2 | +7,8% | −21,4% | −24,2% |

Например, позднее совпадение при 64 наборах: 7,162 → 5,629 мкс.
Раннее совпадение при тех же 64 наборах: 2,440 → 2,631 мкс.
Результат зависит от распределения трафика, а не только длины правила.
При одном наборе нет даже сокращения строк.

В mangle IPv4 legacy позднее совпадение при 64 наборах дало около −23%,
промах −25%, раннее совпадение +7%. nft-compat показывает ту же общую
зависимость, но его величины нельзя переносить на legacy/Keenetic.
Порог «16» — точка этой тестовой матрицы, **не готовая настройка сервиса**.

Время `iptables-restore` RAW для 64 наборов сократилось примерно с
3,5 до 1,4 мс в одном сценарии. Это только обновление строк тестовой цепочки:
создание/наполнение родителя, проверка схем, DNS и остальные этапы полного
apply сюда не входят. Число процессов восстановления таблицы не уменьшается.

## Что подтвердили пакетные проверки

- Первое/последнее совпадение, промах, ограничение порта и отрицательный
  source-селектор дают тот же результат для flat и union.
- Раннее отдельное RETURN/DROP не обходится; два совпадающих дочерних
  набора не приводят к повторной классификации пакета.
- Чужие биты fwmark сохраняются. В mangle отдельный conntrack-тест
  классифицирует первый из 32 пакетов одного соединения; остальные идут
  по восстановленной метке. Оптимизация не ускоряет повторно эту часть пути.
- TTL адреса в дочернем динамическом наборе действует без переписывания
  родителя; статический сосед продолжает совпадать.
- Родитель удерживает ссылки: удалить дочерний набор нельзя, пока
  родитель на него ссылается. Вложенный `list:set` и несовместимый swap
  отклонены проверенным ядром.
- `ipset restore` **не атомарен**: после ошибочной строки предыдущие
  добавления в кандидат остаются. Неподключённый кандидат не влияет на
  активного родителя; проверены swap и обратный swap родителя.

Это не тест аварийного отката всего keen-pbr-sb. Не проверены реальное
переключение failure policy, PPE/аппаратное ускорение, соединения между
LAN/VPN, рестарт сервиса, опустошение/замена конфигурации и загрузка прошивки.

## Требования к возможному внедрению

1. Подтвердить поддержку **ядром и userspace** на целевых Keenetic, затем
   измерить CPU/RAM и apply на небольших/крупных конфигурациях, RAW/mangle,
   IPv4/IPv6, с реальным fast path. Не отключать ускорение ради красивого числа.
2. Группировать только дочерние destination-наборы одного логического
   правила/семейства с неизменными порядком, всеми условиями, действием,
   маской и уже разрешённой failure policy. Не трогать source UDP-peer,
   output detour, исключения или разные правила одного outbound.
3. Сохранять плоский путь для неподдерживаемого backend, одного набора,
   недоказанной совместимости или невыгодного сценария. Не делать новый
   сервисный блокиратор, watchdog или перезапуск.
4. Родители должны принадлежать поколению публикации. RulesOnly может
   переключать цепочку на B, продолжая ссылаться на статические наборы A:
   поколение дочерних наборов нельзя угадывать по имени родителя.
5. Проверять не только заголовок родителя, но и точный упорядоченный список
   членов. Сначала подготовить неподключённого кандидата, затем публиковать
   цепочку. Ошибка частичного `ipset restore` не должна очищать действующие
   наборы. Уборка: снять ссылки цепочек → удалить родителей → удалить
   ненужные дочерние наборы; DNS-наборы/чужие объекты сохранить.
6. Существующий `build_set_teardown_script` обходит наборы плоским списком
   `flush/destroy`. Для графа parent → child этого недостаточно: наивное
   добавление родителя может оставить ссылки или очистить ещё используемый
   child. **В текущем плоском сервисе этот эксперимент не доказывает дефект**;
   это обязательное изменение именно будущего union-пути.
7. Разделить источник данных (`RuleState::set_names`, дочерние наборы) и
   реальную идентичность classifier match (родитель). Доработать verifier,
   MET-01 и diagnostics вместе: агрегированный match не выдавать за
   точную статистику каждого дочернего списка. Старый snapshot не суммировать
   с новым после смены физической формы/поколения.
8. Проверить сохранение/удаление, режимы apply, ошибки загрузки/отката,
   поддерживаемые архитектуры и точный IPK перед продвижением.

**Итог:** кандидат полезен прежде всего для больших составных правил,
но как массовая оптимизация по умолчанию пока не обоснован. Production
backend, API, конфигурация и формат пользовательских данных не изменены.
