# Ручное сравнение сайтов и путей

На дашборде, в карточке проверки маршрута, раскройте
«Сравнить несколько адресов и путей». Проверка начинается только по кнопке.
Открытие карточки, изменение полей и обычное обновление страницы её не запускают.

## Подготовка

1. Введите домены, IP или HTTPS-адреса ресурсов, по одному на строку.
   Например, страницу и адрес не загрузившегося CSS из Network браузера.
   Проверять все ресурсы страницы автоматически не нужно: укажите нужные явно.
2. Выберите пути и IPv4/IPv6. Число проб равно числу сочетаний адреса, пути
   и семейства IP. В одной серии не больше 12 проб.
3. Нажмите «Запустить сравнение». Запросы выполняются по одному, с секундной
   паузой между ними. Автоматических повторов нет.

Серия не запускает выключенные VPN, не перезапускает службы, не меняет
настройки, правила или опубликованное состояние здоровья туннелей.
При этом активные пробы создают настоящий трафик: он может повлиять на
автообучение nfqws2 и его auto.list. Не смешивайте серию с записью неудачной
попытки пользователя, иначе сравнение будет зависеть от самих проверок.

## Что означает путь

- **По действующим правилам** — HTTP-проба использует результат свежей
  диагностики правил: IP из свежего DNS-ответа, полную метку правила и интерфейс
  из поиска маршрута ядра. Для группы
  используется её фактический путь, а не перебор всех участников.
- **Без метки keen-pbr** — запрос без метки keen-pbr с привязкой к интерфейсу,
  который вернул поиск маршрута ядра. Это не обещание «без VPN»: сам роутер
  может иметь VPN в своём маршруте по умолчанию или другие системные правила.
- **Конкретный интерфейсный выход** — используются его уже применённая метка
  и интерфейс из активной конфигурации. Если метки/маршрута нет или ядро
  направляет пробу в другой интерфейс, запрос не выполняется. Ответ через WAN
  не подменяет успешную проверку выбранного VPN. Отдельный выбор групп и
  выходов только по номеру таблицы пока не реализован; группы доступны через
  вариант «По действующим правилам».

Черновик конфигурации не применяется. Поиск маршрута и сам HTTP-запрос —
разные наблюдения; параллельное изменение настроек или failover могут
изменить условия между ними. Во время сравнения лучше не менять маршруты.

## DNS, соединение и HTTP — разные результаты

Каждая строка сначала использует штатную диагностику DNS/правил. Имя
разрешается текущим резолвером роутера, **до** HTTP-пробы выбранного пути.
Это не отдельная проверка DNS через каждый выбранный VPN и не тест bootstrap
DoH/DoT. Источник DNS, сервер, полученные адреса и ошибка показаны отдельно.

Из свежего результата выбирается первый IP нужного семейства. Отсутствие
IPv6 не приводит к незаметной попытке по IPv4. Соседние строки могут получить
разные адреса CDN; сравнивайте фактически выбранные и подключённые IP,
а не только имя сайта. Проверка всех IP одного домена не выполняется.

HTTP-проба:

- один HTTPS **HEAD** на порту 443; сохраняются путь и query введённого URL;
- имя Host/SNI и проверка сертификата сохраняются, IP закрепляется для запроса;
- переходов по redirect, загрузки тела и повторных запросов нет;
- отдельный бюджет HTTP — до 5 секунд в пределах общего бюджета диагностики;
- сохраняются HTTP-код, время попытки, лимит HTTP, общее время, время до
  соединения TCP и TLS, выбранный/подключённый IP, метка, таблица и интерфейс.
  TCP/TLS — значения от начала HTTP-запроса, не независимые длительности фаз.

HTTP 403, 405 или 503 означает, что сервер ответил, но вернул ошибку HTTP.
Некоторые серверы не разрешают HEAD; это не доказательство недоступности
ресурса через GET. DNS-ошибка, отсутствие адреса нужного семейства, отсутствие
маршрута, ошибка TLS, тайм-аут и отсутствие ответа сервера различаются.

Это запрос **с роутера**, а не повтор браузерного соединения из LAN.
Он не доказывает прохождение клиентского трафика через nfqws2, полную загрузку
CSS/картинок, воспроизведение видео, работу голоса Discord или отсутствие DPI.
Страница Discord и его голосовой UDP-путь проверяются разными сценариями.
Недоступный контрольный адрес не позволяет сделать вывод «DPI отсутствует».

## Остановка и отчёт

«Остановить серию» прекращает запуск следующих строк. Уже отправленная
проверка получает свой результат либо завершает ожидание по тайм-ауту.
Штатный бюджет серверной диагностики — 45 секунд, тайм-аут ожидания API
в панели — 60 секунд. Закрытие компонента прекращает очередь новых проб,
но не обещает мгновенно отменить уже начатую работу сервера.

Сетевой сбой проверяемого сайта сохраняется в своей строке и не мешает
проверить следующие адреса. Если сама панель не получила корректный ответ
диагностического API, серия останавливается: это не ошибка всех сайтов.
Несовместимый старый ответ не выдаётся за выполненную проверку нового пути.

После завершения или остановки можно скачать JSON. Он содержит только
выбранные цели/пути, состояния строк, DNS/HTTP-наблюдения и временные метки;
также сохраняется активная область конфигурации и наличие неприменённого черновика;
полные списки правил, устройства и таблица соединений в него не копируются.
Автоматического сохранения или отправки отчёта нет. В URL могут быть личные
параметры; проверьте их, IP и названия VPN перед публикацией.

## API и локальные регрессии

Используется существующий авторизованный `POST /api/routing/test`, по одному
запросу на строку. Новый необязательный параметр не меняет старые вызовы:

```json
{
  "target": "static.example.com",
  "http_probe": {
    "url": "https://static.example.com/style.css?v=2",
    "family": "ipv4",
    "path": "outbound",
    "outbound": "vpn_example"
  }
}
```

`path`: `policy`, `direct` или `outbound`; `outbound` указывается только для
последнего варианта. `family`: `ipv4` или `ipv6`. URL обязан соответствовать
`target`; учётные данные, фрагмент, другой порт и управляющие символы запрещены.
`http_probe` и прежний `http_probe_ip` нельзя применять вместе. Клиент
не задаёт произвольные метку или интерфейс. Схема: `docs/openapi.yaml`.

Регрессии находятся в `frontend/tests/routing-batch.test.tsx`,
`tests/test_routing_http_probe.cpp` и `tests/test_api_test_routing.cpp`.
Проверяются последовательность/остановка, отсутствие запросов при открытии,
отсутствие повторов, DNS/IPv6/HTTP-различия, привязка выхода без fallback в WAN,
сохранение старого API, проверка URL и минимальный экспорт.

Локальные тесты не заменяют визуальную приёмку панели и аппаратную проверку
точного пакета на Keenetic. Для такой приёмки нужны доступный и недоступный
выходы, IPv4/IPv6, остановка в процессе, отсутствие смены статусов остальных
туннелей и неизменность настроек/служб. Обновление правил по результату —
отдельное действие пользователя; фонового сканирования или автоисправления нет.
