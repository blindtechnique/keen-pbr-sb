# Точечная диагностика TCP-ротатора

Статус: локальный инструмент и воспроизводимые семантические тесты. В IPK,
пресеты и штатный запуск он не включён. По отдельному согласованию 13.09.2026
выполнена ограниченная аппаратная запись; наблюдение уже завершено.
GitHub не исправлен. Само наличие файла не активирует наблюдение; нужен
отдельный вызов `start`.

## Что установлено по коду и тестам

Тест использует настоящий `circular` и учёт ошибок из закреплённого
`tests/fixtures/zapret2-v1.0.3/zapret-auto.lua`, наш TCP success detector и
параметры общего пула **из сгенерированного Max**, а не из отдельной тестовой
копии настроек. Отправка пакетов и время моделируются: это не проверка DPI.

При текущих `fails=2`, `retrans=2` и отсутствии `reset`:

1. Два замеченных повторных TCP-пакета дают одну неудачу соединения.
2. `crec.nocheck=true` прекращает дальнейшую проверку этого соединения. Его
   последующие повторы не дают дополнительных неудач; поздний ответ также
   уже не сбрасывает счётчик через success detector.
3. Вторая неудачная сессия к тому же ключу переключает общий `hrec.nstrategy`.
   Новый выбор применяется уже к текущему пакету, а также к следующим пакетам
   старых соединений. Выбор **не закреплён за соединением**.
4. При этом `nocheck` у старого соединения остаётся включённым. Новый выбор
   не означает, что браузер немедленно переподключится или что DPI забудет
   уже заблокированный поток. Принудительного RST в общем пуле нет.
5. Успешное новое соединение другого клиента к тому же адресу и порту тоже
   может сбросить общий счётчик. Диагностический запрос самого роутера может
   влиять на наблюдение; auto.list имеет ещё и свой отдельный учёт.
6. `time=300` — окно накопления неудач, **не таймер принудительной смены
   варианта и не срок хранения успешной стратегии**. После паузы больше окна
   первая новая неудача снова считается первой.
7. Max использует общий ключ по адресу сервера и порту. Другой IP CDN начинает
   с отдельного состояния; разные домены на одном IP могут его разделять.
   Перезапуск теряет RAM-состояние общего TCP-пула. Постоянная память нашего
   companion пока ограничена `gv_tcp`, `yt_tcp`, `yt_quic`.

По сохранённой копии Lua установленного движка v1.0.5 проверено: перечисленные
функции и `circular` совпадают с тестовой v1.0.3; различия полного файла вне
этого участка. Это характеристики алгоритма, а не доказательство, какой
слот фактически вызвал конкретный сбой Chrome. Снимки пакетов такой информации
не содержат. Успех detector означает его порог, не полный HTTP-ответ/страницу.

## Наблюдатель

Файл: `build_scripts/diagnostics/nfqws-rotator-trace.lua`.
Загружать только для согласованной приёмки **после** upstream Lua и нашего
`rotator-telemetry.lua`, до обработки трафика. Его API:

```lua
local api = dofile('/path/to/nfqws-rotator-trace.lua')
local session, error_code = api.start({
    client = '192.0.2.10',
    targets = {'198.51.100.10|443', '198.51.100.11|443'},
    pool = 'tcp_general',
    seconds = 120,
    max_events = 512,
    emit = function(row)
        -- Передать api.format(row) в заранее выбранный приватный журнал в RAM.
        -- Не писать в постоянную flash на каждый пакет и не публиковать журнал.
    end,
})
-- При ошибке API возвращает nil/error_code; не оборачивать в assert при запуске службы.
-- session.stop() завершает наблюдение; session.status() возвращает его состояние.
-- api.header() — заголовок TSV; api.format(row) — одна строка без управляющих байтов.
```

В примере только документационные IP. Рабочие адреса выбираются из новой
записи реальной попытки; список CDN нельзя считать постоянным. Команды
установки или изменения активного профиля здесь намеренно не автоматизированы.

Обязательны точные клиент, пул, 1–8 адресов сервера с портами и обработчик
событий. По умолчанию 120 секунд, 512 событий и 128 наблюдаемых соединений;
жёсткие пределы — 300 секунд, 2048 событий и 256 соединений. Время проверяется
при вызовах ротатора; если трафика нет, отдельный процесс или таймер не нужен.

Журнал содержит направление, относительную TCP-позицию (`sequence`), флаги,
длину payload, идентификатор
соединения, выбор до/после, первый и предыдущий замеченные выборы, счётчики
повторов/неудач и состояния `pending`, `failure`, `success`, `already_finished`.
`slot_after` — выбор оркестратора, **не доказательство выполнения fake/split**:
следующие фильтры payload/range ещё могут пропустить конкретное действие.
Для точного URL и результата браузера нужна отдельная информация из Network.

Наблюдатель не вызывает детекторы/hostkey повторно, не меняет `autostate`,
`lua_state`, параметры, планы, вердикты или счётчики. Он не отправляет пакетов,
не добавляет RST и не управляет службами. Ошибка обработчика/наблюдателя,
исчерпание лимита или перевод часов назад отключают **только наблюдение**.
Исходные ошибки оркестратора не скрываются. Позднее установленный сторонний
Lua-hook не перезаписывается при завершении нашей диагностики.

Payload, SNI, URL, пароли и заголовки HTTP не записываются. IP, порты и временные
метки всё равно являются приватными диагностическими данными. Входящий пакет
до DNAT допускается только по уже наблюдавшемуся точному conntrack, без
расширения фильтра на всех клиентов.

## Локальная проверка и последующая приёмка

```sh
make check-nfqws-rotator-lua
```

Новый набор проверяет многократные зависания, смену выбора в старом соединении,
поздний ответ, новый клиент/адрес, сброс RAM и истечение окна ошибок. Состояния
и вердикты сравниваются с выполнением без наблюдателя. Отдельно проверяются
границы, ошибки sink, IPv6/NAT, изоляция клиента/адресов и отсутствие payload.

Локально 13.09.2026: 85 проверок нового набора прошли как с закреплённой
v1.0.3, так и с сохранённым `zapret-auto.lua` v1.0.5. Среда — Lua 5.3.6 в
изолированном контейнере без сети; это не нативный пакетный цикл nfqws2.
Все десять Lua-наборов и 60 Python-тестов assets/profile/window
прошли. Один отдельный native firewall-тест пропущен, поскольку этот запуск
не имел NET_ADMIN. Полная сборка сервиса и IPK в этот срез не входили.

## Аппаратная запись 13.09.2026 и открытый дефект TLS

По отдельному разрешению выполнен один restart только nfqws2 для временного
observer на текущем Max. Кандидаты и production Lua не менялись; конфиг на
диске сразу восстановлен побайтно. Через 120 секунд наблюдение автоматически
закрылось без повторного restart. Маршрутизация, DNS и VPN не перенастраивались.
Этот старт сбросил RAM общего ротатора: это не сохранённое warm-состояние.

В первой записи основной GitHub получил ответные TLS-данные, Lua зафиксировал
19 исходящих событий одного conntrack со слотом 1. Входящие события выбранным
observer не зафиксированы. Ротация этого соединения не наблюдалась. CSS CDN
не вошёл в первый список адресов; переносить этот слот на сервер стилей нельзя.
Пользователь получил страницу без стилей, но с картинкой. Console показала
многочисленные ERR_CONNECTION_RESET у CSS/JS github.githubassets.com.

Вторая двухминутная запись была только пассивным tcpdump для адресов сервера
стилей: без restart, сигналов и изменений конфига. Пользователь снова получил
страницу без стилей. Зафиксировано 177 входящих открытых TLS fatal decode_error
и 177 close_notify на одном адресе CDN. Сопоставление велось на одном интерфейсе;
потерь tcpdump не было. Это ранний отказ TLS, не просто долгое ожидание TCP.
По [RFC 8446 §6.2](https://www.rfc-editor.org/rfc/rfc8446.html#section-6.2)
decode_error означает неразбираемое TLS-сообщение. По LAN-записи ещё нельзя
доказать подлинность источника ответа или точный виновный вариант fake/split.

**В установленной во время записи версии подтверждён пробел детектора.**
Её keen_pbr_syn_failure_detector передаёт этот случай стандартному детектору,
который распознаёт RST, HTTP-redirect и retransmission, но не TLS alert.
Локальная репродукция с настоящим circular v1.0.5 и production companion:
две свежие сессии с fatal decode_error и нормальным TCP-закрытием оставляют
слот 1 и нулевой счётчик неудач; два входящих RST переключают слот 1 → 2.
Это модель пакетов/общего lua_state, а не replay через нативный движок и NAT.
Она не доказывает фактический слот CDN или доставку alert в общий пул роутера.

## Локальный TLS-фикс и нативная проверка NAT, 13.09.2026

По отдельному согласию подготовлено только локальное исправление. На этом
этапе к роутеру не подключались, конфиги пресетов не меняли, IPK не собирали,
commit/push не выполняли. Работоспособность GitHub этим не подтверждена.

В адаптер детектора общего TCP-пула Max добавлен точечный учёт первого
открытого TLS `fatal decode_error` после наблюдавшегося `ClientHello` в том же
conntrack. Хранятся не более семи позиций байтов первой записи; поддержаны
разбиение, повтор и перестановка TCP-сегментов. Чужая первая запись или
конфликтующее перекрытие выключает этот классификатор для соединения.
`close_notify`, другие alerts, шифрованные записи и поздние ошибки не служат
основанием переключения. Это учёт неудачи варианта, не доказательство DPI.

Счётчик, порог двух неудачных соединений, выбор следующего варианта и защита
от повторного подсчёта остаются у штатного `circular`. Новых RST, таймеров,
перезапусков, постоянной памяти общего пула или запретов действий нет.
Списки кандидатов и остальные пулы этим изменением не затронуты.

Проверки окончательного Lua-файла:

- Новый набор `tests/nfqws_tcp_tls_failure_semantics.lua`: 96 проверок, включая
  отрицательные случаи, повторный подсчёт, изоляцию endpoint и закрытое успешное
  наблюдение. Он включён в штатную цель `check-nfqws-rotator-lua`.
- Все 11 Lua-наборов и 60 Python-тестов assets/profile/window прошли. Один
  дополнительный native firewall-тест штатной цели пропущен без NET_ADMIN.
- Те же 96 проверок отдельно прошли на встроенном LuaJIT 2.1.1756211046
  настоящего nfqws2 v1.0.5. Это проверка Lua-семантики, не сетевых hooks.

Направления проверены отдельно через настоящий пакетный цикл nfqws2 v1.0.5
(`0b8182d24a887059a628d7266577c4ba8e9b8f2d`, x86_64, lua_compat_ver 6).
В одноразовом контейнере без внешней сети созданы клиент, маршрутизатор и
сервер. Сервер отвечает фиксированным alert на настоящий ClientHello;
кандидаты — два no-op, без fake/split. Проверен новый детектор с полным
production companion, затем контроль со штатным старым TLS-поведением.
В каждой схеме — три новых TCP-соединения, все получают исходный alert.

| Локальная схема | Общий Lua-контекст запроса/ответа | Старый детектор | Новый детектор |
|---|---|---|---|
| Без NAT, POSTROUTING/PREROUTING | Да | Не учитывает отказ | Переключает 1 → 2 |
| SNAT, POSTROUTING/PREROUTING | Нет | Не учитывает отказ | Не учитывает отказ |
| SNAT, ответ в FORWARD после обратного NAT | Да | Не учитывает отказ | Переключает 1 → 2 |
| SNAT с заменой порта, POSTROUTING/PREROUTING | Нет | Не учитывает отказ | Не учитывает отказ |
| SNAT с заменой порта, ответ после обратного NAT | Да | Не учитывает отказ | Переключает 1 → 2 |

**Второй дефект воспроизведён нативно:** в схеме POSTROUTING/PREROUTING исходящий
пакет ещё содержит адрес клиента, ответ — адрес WAN до обратного NAT.
nfqws2 создаёт два разных conntrack; alert не связан с исходным ClientHello.
Одна только Lua-правка не исправляет эту интеграцию. Нельзя склеивать клиентов
по одному адресу сервера или считать ответ успехом без совпадения соединения.

Контроль с ответом после обратного NAT стал основанием для следующего локального
среза интеграции, описанного ниже. Натурная приёмка по-прежнему должна отдельно
подтвердить аппаратное ускорение, VPN и текущий Chrome.

Следующий аппаратный шаг требует согласования. В capture включить фактические адреса
CSS/JS и не запускать параллельные router curl к тем же целям: они влияют на
общий счётчик. Полный проход GitHub и TCP 16–20 остаётся неподтверждённым.

Исходные PCAP и адресные журналы остаются в приватном ignored build и не
предназначены для публикации. PCAP snaplen 128 может содержать начало TLS/
шифрованных данных; ограничения payload-free относятся к Lua observer,
не к сетевому захвату.

## Локальная интеграция TCP после обратного NAT, 13.09.2026

Это изменение **нашей интеграции**, не форк nfqws2/zapret2. Штатный `circular`
остаётся владельцем счётчиков и выбора слота. Lua-адаптер keen-pbr-sb добавляет
распознавание раннего TLS-отказа в Max; наш firewall-helper даёт движку видеть
обе стороны одного TCP-соединения. Бинарник nfqws2, его Lua-библиотеки и файлы
vendor-пакета не переписываются.

Генератор добавляет `kpbr_tcp_reply=postnat_v1` рядом с `kpbr_tcp_window=96`
в общий TCP-пул Balanced/Max. Safe, UDP/QUIC, кандидаты и их количество этим
срезом не меняются. Helper проверяет возможность по **argv работающего процесса**,
его PID/starttime, подключённой очереди и установленному companion. Одного
сохранённого файла недостаточно. Установленные на роутере профили автоматически
не переписываются: новый режим появляется при явном применении нового профиля.

Пакетный путь в поддержанной схеме:

| Направление | Наблюдение | Адреса в контексте движка |
|---|---|---|
| Запрос | vendor `nfqws_post`, mangle POSTROUTING до SNAT | клиент → сервер |
| Ответ клиенту | наша цепочка из mangle FORWARD после обратного NAT | сервер → клиент |
| Ответ самому роутеру | та же цепочка из mangle INPUT | сервер → исходный локальный адрес |

`KpbrNfqTcpReply` копирует только распознанные read-only исключения по интерфейсу,
mark/connmark и конечную грамматику штатных TCP-очередей. Сохраняются текущие
интерфейсы, порты, queue number, stock packet window и FIN/RST/SYN-ACK rules.
Входящее расширение окна до 96 пакетов переходит сюда же; исходящее остаётся в
`nfqws_post`. В начале `nfqws_pre` собственный tagged TCP RETURN предотвращает
первую, pre-DNAT обработку. Исходные vendor-правила остаются нетронутыми;
UDP продолжает идти через исходный PREROUTING.

Весь переход — одна транзакция `iptables-restore --noflush` на семейство адресов.
Повторный apply не добавляет правил и не обнуляет их счётчики. Remove удаляет
только собственные tags/цепочку; чужую цепочку с совпавшим именем не присваивает.
Если обновлённый vendor использует неизвестную грамматику, адресные условия или
побочные действия, post-NAT расширение не применяется/снимается. Штатный nfqws2
и маршрутизация не останавливаются. Это не обещание поддержки любой будущей
версии, а отсутствие зависимости обновления vendor-файлов от нашего патча.

Перед штатным пересозданием правил NDM hook `099-keen-pbr-nfqws-tcp.sh` снимает
наши поздние hooks; после `100-nfqws2.sh` hook `110-keen-pbr-nfqws-tcp.sh`
восстанавливает их по фактическим правилам. Команды панели, включая update и
rollback, обрамлены таким же remove/apply. Ошибка необязательного helper не
меняет результат штатного действия и не запускает перезапуск маршрутизации.
Boot hook S53 остаётся одноразовым, наблюдающего демона нет.

Прямой вызов стороннего S51-скрипта из CLI в обход наших событий не перехватывается.
Для такого обслуживания нужен явный remove перед командой и apply после неё.
Гарантия единственной обработки относится к завершённой транзакции и проверенному
порядку событий; она не распространяется на произвольную параллельную правку
firewall или неуспешное снятие hooks.

### Локальные проверки и границы

- 35 сценариев с настоящим nfqws2 v1.0.5: IPv4/IPv6, SNAT и замена порта, запросы
  самого роутера, два клиента с одинаковыми исходными портами, другой входящий
  интерфейс/пул, mark/connmark/processed-mark, порты/интерфейсы вне правил,
  неизменный UDP, remove и цикл NDM pre/vendor-rebuild/post. Каждая ожидаемая
  входящая TLS-запись увидена один раз. Модель другого пула — не реальный VPN.
- Контроль без helper воспроизводит два контекста через SNAT и отсутствие
  переключения. После apply контекст общий, повторные TLS-отказы переводят
  штатный круг 1 → 2. Кандидаты здесь no-op: работоспособность fake/split,
  внешнего сайта и причина реального `decode_error` этим не доказаны.
- 86 Python-тестов assets/profile/window и все 11 Lua-наборов прошли. Два native
  firewall-теста, пропущенные без capabilities, отдельно прошли в изоляции.
  Есть проверка BusyBox sh + awk. 31 тест упаковочного валидатора прошёл;
  новый NDM hook включён в обязательное содержимое IPK.
- Изменённый C++-объект обработчика панели скомпилирован. Это не полная
  backend-сборка и не приёмка собранного IPK.

### Ранний INPUT ACCEPT Keenetic

Read-only аудит выявил недочёт первоначального локального варианта: штатный
INPUT shortcut завершает обработку ответов самому роутеру раньше hook,
добавленного в конец цепочки. Наличие этого правила не доказывает причину
реального сбоя GitHub: первоначальный post-NAT вариант на роутер не ставился.

Исправленный планировщик узнаёт **одну точную проверенную строку**:

```text
-A INPUT -m state --state RELATED,ESTABLISHED -m connndmmark --mark 0x20/0x0 -j ACCEPT
```

Перед ней вставляется собственный TCP hook **со всеми теми же state и
connndmmark условиями**. Это важно: принятие пакета из NFQUEUE завершает текущий
mangle hook, поэтому без этих условий можно было бы пропустить последующую
политику для пакетов, которым native ACCEPT не подходит. Для них сохраняется
обычный hook в конце INPUT. При совпадении условий работает ранняя ветвь;
до поздней тот же пакет не доходит: очередь либо завершает hook, либо
следующий штатный ACCEPT завершает его после возврата из нашей цепочки.

Все предыдущие правила остаются впереди, сама native-строка не удаляется и
не переписывается. Условия NDMS копируются, а не трактуются как обычный
connmark. Позиция считается без собственных старых hooks: прежнее добавление
в конец или перестановка штатного правила исправляются одной `--noflush`
транзакцией; повторный apply ничего не меняет. Совпадение отсутствует,
неоднозначно или содержит другие условия — остаётся только hook в конце
INPUT. FORWARD по-прежнему использует добавление в конец; произвольные
ранние ACCEPT/RETURN не обходятся.

Добавлены 8 Python-регрессий: реальный обезличенный порядок, перенос старого
hook, перестановка native-правила, сохранение предшествующей чужой политики,
неизвестные/дублирующиеся варианты anchor, его удаление, отказ restore и
независимость семейств. Путь также проверен с BusyBox awk. Офлайн-прогон по
ранее снятому полному firewall ставит hook вторым правилом INPUT, сохраняет
все чужие правила и не создаёт IPv6-план, когда nfqws-цепочек там нет.

Из 35 пакетных сценариев 12 посвящены этому порядку INPUT: прежнее добавление
в конец, исправленный hook, SNAT/замена порта, перенос старого hook, remove,
NDM pre/rebuild/post, более ранний чужой ACCEPT, processed-mark входящих
ответов, IPv6 и две ветви при несовпадении условий native ACCEPT. Счётчики
подтверждают выполнение последующей политики при несовпадении: её ACCEPT
останавливает наблюдение, а после нетерминального MARK работает поздний hook.
Старое размещение даёт 0 из 3 входящих TLS-отказов и слот 1;
исправленное — 3 из 3, общий контекст и переключение 1 → 2. Повторной очереди
для ClientHello или тестового входящего alert нет.

В обычном Linux отсутствует Keenetic `connndmmark`: **в этих 12 сценариях
моделируется ранний ACCEPT с булевым тестовым условием**, истинным либо ложным
для соответствующего случая. Test-only wrappers `iptables-save/restore`
переводят только этот селектор между модельной и native-записью: restore
разрешает такую замену лишь в собственных INPUT-командах. Пакеты, NAT,
NFQUEUE, применение транзакции ядром, официальный движок и наш companion
настоящие. В production wrappers нет. Это не интерпретация битов NDMS и
не приёмка проприетарных marks/PPE или прошивки.

Ранний неизвестный ACCEPT/RETURN либо processed-mark исключение всё ещё может
исключить позднее наблюдение: тесты проверяют именно сохранение этой политики,
а не полноту ротатора при ней. Mark/connmark проверяются в новой точке: если
другая цепочка меняет их между исходным
PREROUTING и этой точкой, решение исключения может отличаться. До аппаратного
включения нужно сверить порядок и изменения меток фактического firewall, а не
заявлять эквивалентность любой пользовательской политике. Ускорение, NAT,
маркировка, UDP/QUIC и native-VPN forwarding/SNAT этим helper не настраиваются.

Нативный тест находится в `build_scripts/tests/nfqws_tcp_reply_native.py` и
доступен отдельной целью `make check-nfqws-tcp-reply-native` с
`NFQWS_UPSTREAM=/path/to/zapret2-v1.0.5`. Он не скачивает бинарник; проверяет
версию и SHA-256. Запускается только внутри одноразового Docker-контейнера
`--network none` с NET_ADMIN/NET_RAW/SYS_ADMIN и sysctl=1:
`net.ipv4.ip_forward`, `net.ipv6.conf.all.forwarding`,
`net.ipv6.conf.default.forwarding`, `net.netfilter.nf_conntrack_acct`.
Значения читаются обратно: одного успешного exit code `sysctl -w` недостаточно,
поскольку Docker может оставить `/proc/sys` read-only. Внешних целей, DNS,
паролей роутера и host networking у теста нет.

INPUT-доработка и её проверки выполнены локально по ранее снятому read-only
снимку, без нового подключения к роутеру, IPK, commit/push или публикации.
Следующий отдельный этап — полная сборка и проверки точного IPK, затем
согласованная ограниченная аппаратная приёмка пакета, Chrome, VPN и ускорения.
GitHub/NFQ-01 пока не закрыт.

### Аппаратное уточнение для Alpha, 14.09.2026

Описанная выше Linux-модель не проверяет ABI Keenetic. Последующая проверка
на AArch64 Keenetic обнаружила отдельную несовместимость: ядру нужен
`connndmmark` revision 1 (три `uint32_t`: mark/mask/invert), а старый Entware
терял маску и инверсию при сериализации. Поэтому успешный `--test` не означал
успешный COMMIT. В Alpha добавлен процесс-локальный адаптер
`src/keenetic/connndmmark_compat.c`; он не заменяет системную библиотеку и
уступает будущей штатной поддержке Entware. Реальные COMMIT, проверка и
сериализация правила на Keenetic проверены отдельно от Linux-модели.

На этом подключении отрицательный sequence offset первого fake приводил к
зависанию TLS. Общие TCP-пулы теперь используют рабочий положительный сдвиг
`10000` вместе с `badsum`: одного сдвига недостаточно для гарантированного
отбрасывания fake приёмником. Генератор обновляет «Безопасный»,
«Сбалансированный» и «Максимальный» согласованно. Настоящий TCP-приёмник
проверяется отдельной целью `make check-nfqws-tcp-fake-kernel`; эта проверка
также не заменяет испытание на Keenetic.

После применения исправленного Max на тестовом Keenetic пользователь
подтвердил полную загрузку GitHub в Chrome одним Ctrl+F5: страницу, стили,
логотип README и последние коммиты. Дополнительные загрузки CSS с роутера
также прошли; службы маршрутизации, DNS и VPN для этой проверки не
перезапускались. Полный проход TCP 16–20, длительная стабильность и приёмка
каждого последующего опубликованного IPK этим результатом не доказаны.
