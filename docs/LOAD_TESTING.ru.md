# LOAD-01: измерения на Keenetic

Это методика и конечные диагностические инструменты, не новый watchdog и не
новые ограничения сервиса. Публикация, сборка IPK и переключение рабочих VPN
не входят в запуск измерителя.

## Что именно сравнивать

Не смешивать три разных числа:

1. **1/5/10 одновременных HTTP/DNS-запросов** — отзывчивость панели и DNS.
2. **Генерация конфигурации для 1/5/10 выходов** — время построения JSON и
   выделения памяти Go, без запуска sing-box и применения маршрутов.
3. **1/5/10 реально работающих туннелей в isolated/shared** — отдельная
   аппаратная матрица RSS/CPU, запуска, восстановления и трафика. Первые два
   измерения не заменяют третье.

Для третьей матрицы нужен отдельный Keenetic или согласованное окно на рабочем
роутере. Не отключать пользовательские туннели, не менять процессный режим,
DNS, ускорение или маршруты скрыто ради заполнения таблицы. Синтетические
loopback-прокси и результаты ПК не выдаются за реальный VPN-трафик Keenetic.

## Конечный сбор метрик

`build_scripts/diagnostics/keenetic-load-snapshot.sh` читает `/proc` и датчики:
CPU, MemAvailable, swap, VmRSS процессов, NFQUEUE, RX/TX интерфейсов. Он не
пишет на роутер, не запрашивает сайты, не читает содержимое VPN-конфигов,
не записывает пакеты и не вызывает управляющий API. По умолчанию 61 снимок
через 5 секунд; аргументы ограничены 2..720 снимками и интервалом 1..60 секунд.
Это верхние границы диагностического задания, не настройки рабочего сервиса.

Процессы связываются по PID **и времени запуска**, а не только по имени.
Запущенный через Entware `ld.so` sing-box тоже учитывается; из аргументов
проверяется только токен имени бинарника, сами аргументы не экспортируются.
Кратковременный дополнительный dnsmasq не считается автоматически перезапуском
основного процесса.
Исчезновение процесса во время сбора RSS делает снимок непригодным для
полного сравнения, а не превращается в нулевую память.

CPU системы нормирован на всю доступную CPU-ёмкость; CPU процесса — на одно
ядро, поэтому эти проценты нельзя складывать напрямую. Iowait не включён в
busy CPU. Величина RSS включает общие страницы: сумма RSS нескольких процессов
не является их уникальной физической памятью. На проверенном ядре `/proc/*/smaps`
нет; PSS не имитируется. Максимум в отчёте — максимум **среди снимков**, не
гарантированный пик между ними.

CPU процесса keen-pbr не включает работу кратковременных дочерних `iptables` /
`ipset`. Общая загрузка CPU включает их вместе с остальными службами роутера.
Поэтому один столбец CPU основного процесса не является полной ценой сервиса.

Счётчики NFQUEUE читаются как накопительные. Дельты пригодны только при
неизменном владельце/наличии очереди; uint32-переполнение номера пакета
обрабатывается отдельно. Номер пакета не является счётчиком полезных байтов,
а нулевые потери NFQUEUE не доказывают доступность каждого сайта. RX/TX
интерфейсов включают посторонний трафик и накладные расходы SSH-наблюдения;
не складывать bridge/физический/VPN интерфейсы как независимый трафик.

Пример с компьютера, на котором есть Python 3 и OpenSSH:

```sh
python build_scripts/diagnostics/keenetic-load.py capture \
  --router 192.168.1.1 --ssh-port 222 --key /absolute/path/to/key \
  --output build/load-local/clients-1.jsonl \
  --concurrency 1 --rounds 12 --interval 5 --timeout 2
```

Каталог результата создаётся заранее. Адрес/ключ выбираются владельцем;
StrictHostKeyChecking включён. Файлы создаются эксклюзивно, старые результаты
не перезаписываются. `.tsv` — метрики, `.jsonl` — пробы, `.ssh.log` — ошибки
SSH, `.summary.json` — сводка. Скрипт не устанавливается как служба/cron.

Пробы — только `GET /api/auth/status` по прямому LAN HTTP и A-запрос
`example.com` к указанному роутеру. Новый TCP на запрос; системный HTTP-прокси
не используется, перенаправления не выполняются. DNS-кэш не очищается:
это **повторные, преимущественно кэшированные запросы**, не замер холодного
upstream DNS. NXDOMAIN/SERVFAIL, пустой/обрезанный/чужой ответ не считаются
успехом. Пробы не проходят авторизацию и не доказывают скорость тяжёлых
авторизованных API/всей страницы приложения.

После успешного прогона повторить с `--concurrency 5`, затем `10` и новыми
именами файлов. DNS и HTTP выполняются отдельными сериями, максимум N
одновременных запросов, не 2N. При ошибке не увеличивать нагрузку автоматически.
Время запуска интерпретатора/создания HTTPS trust store не должно попадать
в сетевую задержку: для HTTP используется прямой `HTTPConnection`.

Для пассивного наблюдения передать shell-скрипт через stdin SSH, например:

```sh
ssh -T -p 222 -i /absolute/path/to/key \
  -o BatchMode=yes -o StrictHostKeyChecking=yes root@192.168.1.1 \
  '/opt/usr/bin/sh -s -- 61 5' \
  < build_scripts/diagnostics/keenetic-load-snapshot.sh > build/load-local/passive.tsv
python build_scripts/diagnostics/keenetic-load.py summarize-snapshot build/load-local/passive.tsv
```

Синтаксис перенаправления выше для POSIX-shell. PowerShell-пользователь может
пользоваться `capture`: двоичный stdin OpenSSH формируется Python без CRLF/BOM.
Неполный журнал не считается успешным измерением.

## Чистые микрозамеры на аппаратуре

Go-бенчмарки в `extensions/transport-manager`:

- `BenchmarkLoadConfigBuild`: реальная генерация isolated/shared и JSON,
  1/5/10 синтетических VLESS/TLS выходов.
- `BenchmarkLoadInputBoundaries`: реальные декодеры тела API, 64 КиБ/4 МиБ,
  превышение на байт, 512/513 узлов; ожидаемые отказы проверяются внутри цикла.
- `TestLoadRuntimeLogBoundaryWithOpenWriter`: порог 2 МиБ, превышение, повторная
  запись уже открытым append-дескриптором. Только собственный временный файл.

Для нужной архитектуры отдельно собрать `go test -c` двух пакетов; это
**тестовые исполняемые файлы, не IPK**. На роутере использовать новый закрытый
каталог, синтетические данные, TMPDIR внутри этого каталога, GOMAXPROCS=1,
низкий приоритет и короткий `-test.timeout`. Не запускать весь набор тестов
неизбирательно на рабочем роутере.

```sh
GOMAXPROCS=1 GOMEMLIMIT=96MiB TMPDIR=/absolute/owned-test-dir/tmp \
  nice -n 10 ./transport-load.arm64.test \
  -test.run '^TestLoadRuntimeLogBoundaryWithOpenWriter$' \
  -test.bench '^BenchmarkLoadConfigBuild$' -test.benchtime=20x -test.count=3 \
  -test.benchmem -test.timeout=60s
GOMAXPROCS=1 GOMEMLIMIT=96MiB TMPDIR=/absolute/owned-test-dir/tmp \
  nice -n 10 ./api-load.arm64.test -test.run '^$' \
  -test.bench '^BenchmarkLoadInputBoundaries$' -test.benchtime=20x -test.count=3 \
  -test.benchmem -test.timeout=60s
```

GOMEMLIMIT — мягкая цель Go GC, не жёсткое ограничение RSS. Значения заданы
только для тестовых процессов и не меняют окружение работающего сервиса.
`B/op` — суммарные выделения на операцию, не одновременно занятая память;
`ns/op` генерации не означает время применения/восстановления маршрутов.

## Остальная обязательная матрица

Перед рекомендациями для установки остаются:

- Реальные 1/5/10 VPN: одинаковый протокол, MTU, нагрузка, сервер и настройка
  ускорения, отдельно idle и трафик, isolated/shared; все побочные службы
  фиксируются. Не переносить автоматически AArch64-числа на MIPS.
- Большие списки: загрузка/декодирование SRS и подписок, применение и
  восстановление DNS/маршрутов. Существующие ограничения: подписка 1 МиБ/
  512 узлов; SRS по умолчанию 16 МиБ сжатых/64 МиБ распакованных данных плюс
  ограничения структур/строк из `src/lists/srs_decoder.hpp`. Эти значения —
  границы парсера, не доказанный ресурсный бюджет роутера.
- NFQWS: продолжительное видео, параллельные загрузки, CPU/RSS/очередь,
  потери и пользовательский результат. 5–10 минут — короткая нагрузочная
  выборка, не суточная проверка устойчивости и не тест на утечку памяти.
- Недоступный DNS — отдельный тестовый resolver/стенд. Не выключать домашний
  DNS ради опыта. Проверка задержки при рабочем DNS не закрывает этот пункт.
- Журналы: проверяется фактический объём между циклами reconciliation и
  продолжение записи. Текущая очистка при превышении 2 МиБ не означает
  абсолютно жёсткую границу файла каждую миллисекунду.

## Проверка инструментов

```sh
python -m unittest discover -s build_scripts/tests -p test_keenetic_load.py -v
```

Покрыты знаменатели CPU, единицы памяти, PID reuse, неполные результаты,
смена владельца NFQUEUE/переполнение счётчика, DNS-ошибки и прямой HTTP без
переадресации. Локальные журналы с именами интерфейсов, адресом роутера и
моделью хранятся в игнорируемом `build/`; не публиковать их автоматически.
