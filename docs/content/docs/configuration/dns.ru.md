Настройки DNS используйте, если хотите, чтобы домены из списка разрешались через определённый DNS-сервер — как правило, тот же VPN, который пропускает соответствующий трафик.

При установке пакета на роутере keen-pbr обычно сам заботится об интеграции с dnsmasq. Большинству пользователей достаточно задать:

- `system_resolver` (оставьте значения по умолчанию)
- `servers`
- `rules`
- `fallback`

## Конфигурация

В локальной Alpha подключено экспериментальное дополнительное обучение адресов
по DNS, TLS SNI, HTTP Host и QUIC Initial. Оно **выключено по умолчанию**.
В «Настройки → Дополнительно → Обучение по DNS и именам соединений» есть два
независимых переключателя. Они меняют только черновик; нужны сохранение и применение.
dnsmasq остаётся необходимым и продолжает работать. Принудительный DNS — отдельная
настройка, эти переключатели его не включают.

В JSON используются `dns.learning.dns` и `dns.learning.l7`. Для совместимости
отсутствующее или `null` значение каждого переключателя наследует
`dns.passive_learning` (по умолчанию `false`). Например,
`"dns": {"learning": {"dns": false, "l7": true}}` включает только L7.
Обычное сохранение других настроек не переписывает старое представление.

На обзоре под проверкой DNS раскройте «Обучение по DNS и именам соединений».
Там показаны состояние каждого обработчика, интерфейсы, счётчики и техническая
причина недоступности. «Активен» означает настроенный перехват и живой обработчик,
а не проверенную маршрутизацию сайта или исправность VPN. Нет показаний — не сбой;
при потере связи с потоком событий показания обозначены как последние полученные.
Нулевые счётчики также не доказывают неисправность. Они сбрасываются при
пересоздании обработчика. Просмотр не отправляет проб и не меняет маршруты.

Обучение использует списки действующих правил маршрутизации. В область входят
явные `route.inbound_interfaces` и включённые клиенты встроенных VPN с подтверждённым
входящим интерфейсом. Для VPN с пулом адресов одновременно проверяются интерфейс
и подсеть клиента. Привязки к LAN в прошивке или сохранённого неподтверждённого пула
недостаточно. Пулы IPv4 и IPv6 учитываются отдельно; выключенный в сервисе IPv6
не перехватывается. Пустой список LAN не означает «вся сеть»: остаются только
подтверждённые входящие интерфейсы включённых VPN-клиентов, но не произвольный WAN.

Исключения VPN проверяются до перехвата: по источнику для L7 и по получателю для
DNS-ответа. Выключенный VPN-пул на общем мосту больше не исключает остальных клиентов
LAN. На мосту пропускается весь исключённый пул, без использования входящего
физического порта, который нельзя так же проверить у ответа. Для VPN-клиентов
на мосту этот мост пока нужно явно выбрать. Исключение DNS REDIRECT на безадресном
интерфейсе не отключает пассивное обучение и не меняет действующий путь DNS.

DNS-ответы обрабатываются через отдельную очередь 43053 с `queue-bypass` и только
при подтверждённой поддержке ядром FAIL_OPEN. На старых ядрах удержание DNS не
включается; dnsmasq и доступный пассивный L7 продолжают работать. Копии TCP 80/443
и UDP 443 передаются в NFLOG 43054 с ограничением частоты. Занятые очереди других
программ, включая nfqws, не перехватываются.

При STOP собственные правила перехвата удаляются, затем обработчик закрывается.
Модуль не меняет здоровье VPN и не перезапускает службы.
Запросы очистки сохраняют семейство адреса клиента: AAAA, полученный по IPv4,
обучает IPv6-набор, но не доказывает IPv6-адрес клиента (и наоборот).
После успешного обучения существующий обработчик маршрутизации может удалить
до четырёх точных записей conntrack за один запрос, чтобы клиент подключился по
новому маршруту. Проверяются действующее поколение правил, их порядок, адреса,
протокол и порты, наличие адреса в наборе ядра и подтверждённая запись обучения.
Правила «напрямую», блокировки и «VPN для устройства» сохраняют свой приоритет.
Правильно направленные соединения, чужие метки, пробросы портов и другие зоны
conntrack не очищаются. Запрос ограничен по времени; при занятости обработчика,
неизвестном состоянии, STOP или смене конфигурации он пропускается без повторов.
Общего сброса таблицы нет. Это не бесшовный перенос: приложению может понадобиться
повторить соединение, а аппаратное ускорение пока не проверено на роутере.
Значение `false` у `daemon.reconnect_unmarked_flows_on_routing_change` отключает
и эту очистку, не отключая само DNS/L7-обучение.
ECH и трафик без видимого имени домена могут остаться неопознанными. Это ещё не
замена dnsmasq и не завершённая аппаратная приёмка: на роутеры эта локальная
версия не установлена.

```json { filename="config.json" }
{
  "dns": {
    "system_resolver": {
      "type": "dnsmasq-nftset",
      "address": "127.0.0.1"
    },
    "servers": [...],
    "rules": [...],
    "fallback": ["google_dns", "quad9"]
  }
}
```

| Поле | Тип | Описание |
|---|---|---|
| `system_resolver` | object | Как keen-pbr обновляет dnsmasq в системе |
| `servers` | array | Определения DNS-серверов |
| `rules` | array | Правила сопоставления списков DNS-серверам |
| `fallback` | array of string | Упорядоченные теги DNS-серверов для запросов, которые не соответствуют никакому правилу |
| `bootstrap` | array of string | До восьми тегов обычных DNS-серверов для поиска адресов DoH-серверов. Не резервный DNS сайтов. |
| `dns_test_server` | object | Опциональный встроенный DNS-пробник для расширенного устранения неполадок |
| `client_dns_enforcement` | object | Принудительный DNS клиентов: `{"enabled": true}` прозрачно перенаправляет обычный DNS (порт 53) с входящих интерфейсов на локальный резолвер и блокирует DNS-over-TLS (порт 853, отключается `"block_dot": false`). DoH на порту 443 универсально заблокировать нельзя. |

## Сигнал браузерному Secure DNS

`dns.firefox_doh_canary` управляет сигналом Firefox использовать DNS сети.
Отсутствующее значение/null означает true и сохраняет прежнее поведение.
Значение false убирает созданную панелью строку `address=/use-application-dns.net/`.
Галочка также доступна рядом с DNS клиентов в основных настройках; изменения
сохраняются и применяются обычным способом.

Firefox учитывает сигнал для автоматического DoH, но не переопределяет ручной
выбор пользователя. [Документация Mozilla](https://support.mozilla.org/en-US/kb/canary-domain-use-application-dnsnet).
Настройка не управляет Chrome, Edge и Яндекс.Браузером, не блокирует HTTPS-резолверы.
DNS-провайдер роутера и управление портами 53/853 от неё не зависят.

## System Resolver

`dns.system_resolver` сообщает keen-pbr, как проверять состояние dnsmasq после изменений конфигурации.

При обычной установке пакета на роутер вам обычно не следует изменять эти настройки.

| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `type` | string | да | Тип интеграции резолвера: `dnsmasq-ipset` или `dnsmasq-nftset` |
| `address` | string | да | Адрес резолвера, используемый для интеграции и проверок состояния через TXT, например `"127.0.0.1"` или `"127.0.0.1:5353"` |

## DNS Test Server

`dns.dns_test_server` опционален. Он mainly полезен при устранении неполадок с DNS, когда вы хотите, чтобы keen-pbr предоставил простой тестовый DNS-listener.

| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `listen` | string | да | IPv4-адрес прослушивания в форме `host:port`, например `"127.0.0.88:53"` |
| `answer_ipv4` | string | нет | IPv4-адрес, возвращаемый в ответе DNS-пробника (`nslookup check.keen.pbr`). По умолчанию — хост-часть из `listen`. |

```json
{
  "dns": {
    "dns_test_server": {
      "listen": "127.0.0.88:53"
    }
  }
}
```

Когда HTTP API включён, вы можете проверить, работает ли ваш DNS, через веб-интерфейс.

## DNS-серверы

Каждый сервер имеет тег, опциональный `type`, опциональный `address` и опциональный `detour`.
Значения тега DNS-сервера должны соответствовать `^[a-z][a-z0-9_]*$`, быть не более 24 символов и должны быть уникальными.

| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `tag` | string | да | Уникальный идентификатор для этого DNS-сервера |
| `type` | string | нет | `static` (обычный DNS, по умолчанию), `keenetic` (DNS роутера) или `doh` (DNS через HTTPS) |
| `address` | string | для `static` и `doh` | Для обычного DNS — IP с необязательным портом, например `"10.8.0.1:5353"` или `"[2001:4860:4860::8888]:5353"`. Для DoH — HTTPS URL, например `"https://dns.example/dns-query"`. |
| `ips` | array of string | нет, только `doh` | Фиксированные IPv4/IPv6-адреса DoH-сервера без портов, до 16 адресов. При их указании bootstrap не используется. |
| `detour` | string | нет | Outbound для использования при обращении к этому DNS-серверу |

Поле `detour` полезно, когда DNS-сервер должен быть доступен через конкретное соединение, обычно тот же VPN, который будет переносить соответствующий трафик.

```json { filename="config.json" }
{
  "dns": {
    "servers": [
      {
        "tag": "vpn_dns",
        "type": "static",
        "address": "10.8.0.1:5353",
        "detour": "vpn"
      },
      {
        "tag": "google_dns",
        "address": "8.8.8.8"
      },
      {
        "tag": "google_dns_v6",
        "address": "[2001:4860:4860::8888]:53"
      },
      {
        "tag": "keenetic_dns",
        "type": "keenetic"
      }
    ]
  }
}
```

### `type: keenetic` (встроенный DNS роутера через RCI)

На роутерах Keenetic, `type: "keenetic"` сообщает keen-pbr повторно использовать текущие встроенные настройки DNS роутера автоматически.

Правила и поведение:

- Разрешён максимум один элемент в `dns.servers` с `type: "keenetic"`.
- Для `type: "keenetic"` поле `address` не должно быть задано (адреса берутся из RCI).
- keen-pbr читает неспециализированные (unscoped) строки `dns_server = ...` из политики прокси **System**.
- Если есть неспециализированные зашифрованные апстримы (DoH/DoT), используются все такие серверы по порядку.
- Иначе используются все неспециализированные plaintext-апстримы по порядку.
- Записи `static_a` / `static_aaaa` из политики System также попадают в сгенерированную конфигурацию dnsmasq.

### Как работает `detour`

Для обычного DNS `detour` создаёт правило firewall для IP и порта DNS, включая запросы самого роутера. Это также может влиять на клиентов, которые обращаются к этому IP и порту напрямую. Для DoH выход задаётся меткой HTTPS-соединения посредника; общего правила на порт 443 не создаётся. Поведение при недоступности выхода определяется существующей политикой маршрутизации этого выхода.

Например, если `vpn_dns` имеет `detour: "vpn"`, тогда DNS-запросы к `vpn_dns` также пойдут через `vpn`.

## DNS-правила

Правила сопоставляют списки одному или нескольким DNS-серверам. В редакторе можно выбрать несколько серверов по их псевдонимам; в конфигурации сохраняются технические теги.

| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `enabled` | boolean | нет | Активно ли это правило. `false` отключает его. `true`, отсутствует или `null` все означают включено. |
| `list` | array of string | да | Имена списков, домены которых должны разрешаться этим сервером |
| `servers` | array of string | да, для новых правил | Непустой список уникальных тегов DNS-серверов |
| `server` | string | нет | Совместимость со старым форматом: один тег вместо `servers` |

```json { filename="config.json" }
{
  "dns": {
    "rules": [
      {
        "enabled": true,
        "list": ["my_domains", "remote_list"],
        "servers": ["vpn_dns", "vpn_dns_backup"]
      }
    ]
  }
}
```

Если `enabled` отсутствует или установлен в `null`, DNS-правило всё равно обрабатывается как включённое.

Все выбранные серверы должны быть добавлены в разделе «DNS-серверы». Каждый сохраняет свой выход (`detour`). Если ответы должны приходить только через VPN, выбирайте серверы с соответствующим выходом, включая дополнительные.

В локальной Alpha несколько серверов объединяются в одну группу собственного DNS-посредника keen-pbr. В группе можно смешивать обычный DNS и DoH. Посредник чередует начальный сервер запросов; при тайм-ауте, отказе или SERVFAIL пробует следующий и временно пропускает сбойный. Ответ NXDOMAIN («имя не существует») считается ответом, а не поводом спрашивать другие серверы. Это не строгая схема «основной → резервный». Одиночный обычный DNS остаётся прямой целью dnsmasq. Если несколько правил ссылаются на один список, сохраняется прежний приоритет первого включённого правила; прямые привязки доменов у DNS-сервера по-прежнему важнее правил списков.

Старые файлы с `server` читаются без обязательной перезаписи. Редактор сохраняет правило в формате `servers`. Не задавайте противоречивые значения обоих полей: если указаны оба, `server` должен совпадать с первым элементом `servers`. Пустой массив не возвращает старый сервер автоматически. При удалении одного сервера правило сохраняется с оставшимися; удаление последнего удаляет зависимое правило после подтверждения.

## Собственный DNS-over-HTTPS (локальная Alpha)

В редакторе DNS-сервера выберите «DNS-over-HTTPS (DoH)», введите HTTPS-адрес из документации провайдера и выберите выход. Затем назначьте этот сервер списку или включите его в общий DNS. Одного создания записи недостаточно, чтобы использовать её для всех сайтов.

Если адрес содержит имя, сервис сначала должен узнать IP самого DoH-сервера. Для этого задайте один из вариантов:

1. «Фиксированные IP DoH-сервера» — до 16 IPv4/IPv6 без порта. HTTPS всё равно проверяет сертификат по имени из URL.
2. «DNS для поиска адреса DoH-сервера» — до восьми уже установленных обычных DNS-серверов. Это общий bootstrap для всех DoH-серверов. Он опрашивает серверы по порядку с их собственными выходами; выход DoH задаётся отдельно.

Bootstrap не является резервом для запросов сайтов. Не выбирайте локальный резолвер роутера: он может вернуть запрос в тот же DoH. Без bootstrap, фиксированных IP или числового адреса в URL имя не разрешается через системный DNS автоматически. Это исключает такую зависимость по кругу.

Для HTTPS нужны доверенные CA-сертификаты (`ca-bundle` в Entware). TLS-проверка не отключается. URL с логином, паролем или фрагментом после `#` не поддерживается. При отсутствии ответа DoH не переводит VPN в состояние «не работает» и не перезапускает его.

Изменения сохраняются только кнопкой сохранения. Существующие записи остаются обычным DNS, пока вы сами не измените тип. В расширенном редакторе используются `type: "doh"`, `address: "https://…/dns-query"`, необязательный массив `ips` и общий массив тегов `dns.bootstrap`.

Dnsmasq передаёт запросы локальному DNS-посреднику на `127.0.0.89`. Для каждой из максимум 32 групп он резервирует порт, свободный одновременно для UDP и TCP, в диапазоне `15355–15482`. Порт `5355` остаётся свободным для SMB/LLMNR Keenetic; занятые порты посредник пропускает. В конфигурацию и контрольную сумму dnsmasq попадают именно зарезервированные порты. Одинаковые упорядоченные группы общего DNS и правил списков используют один порт; неиспользуемые DoH-записи не запускают посредник. Группы только из обычных DNS не требуют CA-сертификатов. Посредник запускается до переключения dnsmasq. При ошибке применения прежняя конфигурация восстанавливается; при выключении службы его адрес не остаётся в прямом резервном DNS — сохраняются только реальные обычные DNS без VPN-выхода. Остановка отменяет незавершённый bootstrap.

Дополнительное DNS NFQUEUE/L7 включается отдельно через `passive_learning` и не отменяет dnsmasq. HTTPS-соединения пока открываются заново для каждого запроса, чтобы не переиспользовать соединение другого выхода или старого IP. Производительность на роутерах и аппаратная приёмка ещё не проверены. Штатные настройки Keenetic автоматически не переключаются.

## Интеграция с dnsmasq

При установке пакета на роутер вам обычно не нужно настраивать dnsmasq вручную.

{{% details title="Ручная интеграция с dnsmasq (расширенная)" closed="true" %}}
keen-pbr предоставляет подкоманду `generate-resolver-config`, которая выводит конфигурацию dnsmasq в stdout.

Поддерживаются два типа резолверов:

| Тип резолвера | Стиль директивы | Использовать с |
|---|---|---|
| `dnsmasq-ipset` | `ipset=` | бэкенд iptables/ipset |
| `dnsmasq-nftset` | `nftset=` | бэкенд nftables |

Пример интеграции с dnsmasq:

```text
conf-script=/usr/sbin/keen-pbr generate-resolver-config dnsmasq-nftset
```

Перезапустите dnsmasq после добавления этой строки.

```json { filename="config.json" }
      }

    "fallback": ["google_dns", "google_dns_v6"],
    "system_resolver": { "address": "127.0.0.1" }
  }
}
```

Когда домен в сопоставленном списке разрешается, dnsmasq добавляет полученный IP-адрес во внутренний набор, используемый keen-pbr. Трафик на этот IP затем может быть маршрутизирован через правильный outbound.
