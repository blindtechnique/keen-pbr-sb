## Назначение alpha

Alpha предназначена для проверки изменений и технического знакомства с проектом. Это не обещание стабильности на любой модели роутера. Конкретный установленный пакет определяется полным номером сборки с датой и временем, а не только основным номером версии.

**Новая линия: 3.3.2 · Alpha, сентябрь 2026.** Ветка включает актуальную базу main и последующие исправления обновления, диагностики и интеграции nfqws2 с Keenetic. Полная версия IPK имеет вид `3.3.2-YYYYMMDDhhmmss`: суффикс — дата и время исходного коммита в UTC. Она указана в названии [подписанного Alpha-выпуска](https://github.com/blindtechnique/keen-pbr-sb/releases), имени IPK и панели; одинаковый номер `3.3.2` не означает одинаковые сборки.

### Что изменилось в этой Alpha

- Добавлена совместимость с nfqws2-keenetic 1.3.1: распознаётся его стандартная конфигурация, исправлена проверка TCP-портов PPE, удалена неподдерживаемая команда `reload`. Safe/Balanced/Max не изменены; штатный запуск nfqws2 1.3.1 добавляет `--fastpath-workaround=auto`, если режим не задан явно. [Подробности и границы проверки](docs/NFQWS_1_3_COMPATIBILITY.ru.md).
- Для скачивания обновлений keen-pbr-sb можно выбрать обычный маршрут, VPN или группу. Настройка действует в панели и штатном консольном установщике; недоступный выбранный VPN не подменяется прямым подключением. Первоначальная загрузка установщика внешним `wget`/`curl` и загрузка зависимостей `opkg` этой настройкой не управляются. [Описание и приёмка](docs/UPDATE-DOWNLOAD-VPN.ru.md).
- Проверка конфигурации nfqws находит пустые действия, некорректные и повторные объявления blob в собранной команде; ошибки показываются с понятными пояснениями и указанием поля.
- Регулярные проверки туннелей выполняются в отдельной ограниченной очереди: ручной замер недоступного выхода и длительные фоновые задачи больше не занимают её работников. Это исправление воспроизводимого голодания очереди; отсутствие повторения исторического инцидента проверяется на точном IPK.
- В Balanced/Max расширено наблюдение за поздними TCP-отказами до включения домена в автосписок nfqws2. Картинки и видео, зависающие после первых килобайт ответа, теперь попадают в более длинное окно штатного детектора. Safe не изменён этой доработкой.
- На дашборде добавлено ручное сравнение нескольких сайтов/ресурсов через выбранные пути и IPv4/IPv6. Серия ограничена 12 пробами, не запускает выключенные VPN и не меняет их опубликованное состояние. [Методика и ограничения](docs/SITE_COMPARISON.ru.md).
- Снимок счётчиков правил находится в «Диагностика → Расширенная диагностика» и запрашивается только кнопкой. Это частичный учёт совпадений в firewall, а не полный трафик VPN или сайта. [Что именно измеряется](docs/RULE_COUNTERS.ru.md).
- Парсеры VPN-ссылок и подписок дополнены воспроизводимыми fuzz-тестами; исправлен найденный случай некорректного входа TUIC. [Проверки парсеров](docs/GO_FUZZING.ru.md).
- Обновление списков не должно останавливать маршрутизацию; выключенные пользователем прокси сохраняют своё состояние при обновлении пакета и подписки.
- Обычное обновление из панели использует текущую авторизованную сессию. При временном исчезновении backend панель продолжает отслеживать ту же установку, а не запускает её повторно из-за сетевой ошибки.
- Общий TCP-ротатор учитывает ранние сбросы, повторные передачи и реальные ответы; `googlevideo` получил отдельную логику в «Сбалансированном» и «Максимальном». В Max сохранён экспериментальный `syndata`.
- Исправлена совместимость расширенного TCP-окна с настоящим ABI `connndmmark` в Keenetic. В первых fake-вариантах общего TCP-пула сохранён рабочий положительный сдвиг sequence number и добавлена заведомо неверная TCP checksum: ложные данные не должны попадать в настоящий поток сервера.
- Диагностика nfqws2 показывает применимость конкретных профилей и пересечения доменных/IP-условий; в списках появились подсказки по источникам и проблемам загрузки.

**Граница проверки:** исправленные Max и Balanced прошли повторную браузерную проверку GitHub (страница, стили, логотип README и последние коммиты), проблемного CDN, YouTube и обычного сайта на тестовом Keenetic. Это проверка конкретного подключения, не гарантия для всех провайдеров и не подтверждение полного TCP 16–20. Новые C++-изменения диагностики и установка каждого нового IPK требуют отдельной аппаратной приёмки; CI не заменяет её.

`list:set` пока не используется рабочим firewall. [Исследование SET-01](docs/LIST_SET_RESEARCH.ru.md) показало сокращение числа строк и выигрыш на больших составных правилах в локальном стенде, но не универсальное ускорение. Порог включения не переносится с настольного Linux на Keenetic без измерений.

Состав конкретного IPK нужно сверять с его выпуском: наличие функции в исходниках не означает её наличие в ранее скачанной сборке. Короткая пользовательская инструкция находится в [README стабильной ветки](https://github.com/blindtechnique/keen-pbr-sb/blob/main/README.md).

keen-pbr-sb — независимый открытый проект. Он не предоставляет VPN-серверы и не заменяет KeeneticOS, sing-box или движок обхода DPI zapret2.

## В чём практическое преимущество

- **Один набор правил для разных транспортов.** Нативный WG/AWG, другой готовый интерфейс Keenetic и TUN sing-box могут участвовать в общих правилах и резервных группах. Выбор транспорта не требует отдельной системы списков и DNS для каждого протокола.
- **sing-box не становится вторым владельцем маршрутизации.** Он обеспечивает прокси-транспорт; марки, policy routing, доменные списки и выбор резервного выхода остаются в keen-pbr.
- **SRS не делает sing-box обязательной зависимостью.** Встроенный декодер позволяет использовать совместимые бинарные rule-set со штатным VPN Keenetic, не устанавливая прокси-ядро только ради списков.
- **nfqws2 — не просто кнопка запуска.** Добавлены согласованные пулы стратегий, независимая ротация, наблюдение за её состоянием, ограниченное сохранение удачных вариантов и восстановление наших Lua-доработок при обновлении через панель.
- **Входящий VPN и исходящий VPN — отдельные роли.** Клиент встроенного VPN-сервера Keenetic может пользоваться теми же правилами, DNS и исходящими туннелями, что и домашние устройства.
- **Диагностика связывает несколько слоёв.** Можно проверить DNS, совпадения со списками, выбранный выход, состояние правил и соединений, а не ограничиваться значком «процесс запущен».

Это преимущества сочетания функций и архитектуры. Здесь нет утверждения, что отдельные возможности отсутствуют у всех остальных проектов, или что наш сервис быстрее без сравнительных измерений.

## Архитектура

| Компонент | Что делает | Чего не должен делать |
|---|---|---|
| `keen-pbr`, C++17 | API, конфигурация, списки, DNS-интеграция, маркировка, таблицы маршрутизации, группы и диагностика | Подменять протокольные реализации sing-box или прошивки |
| `transport-manager`, Go | Управляемые процессы sing-box, генерация и проверка конфигов, состояние транспортов | Создавать конкурирующую систему `ip rule` и выбирать правила для сайтов |
| sing-box | Прокси-соединения и TUN-интерфейсы | Включать собственный `auto_route` или перехват DNS в управляемом конфиге |
| dnsmasq | DNS и заполнение адресных наборов для доменных правил | Определять имя HTTPS-сайта, если клиент обошёл DNS роутера |
| nfqws2 / zapret2 | Обработка выбранного прямого трафика и выполнение DPI-стратегий | Служить VPN или универсальным маршрутизатором |
| KeeneticOS | Штатные сетевые интерфейсы и VPN, конфигурация прошивки | Быть заменённой конфигурацией sing-box |
| WebUI, React/TypeScript | Настройка и отображение состояния через API | Требовать запущенного Node.js/Bun на роутере |

Упрощённый путь доменного правила:

```text
DNS-запрос клиента → dnsmasq → IP-набор соответствующего списка
                                      ↓
Пакет → условия правила → метка → таблица/группа → выбранный выход
                                                   ├─ нативный VPN Keenetic
                                                   ├─ TUN sing-box → прокси
                                                   ├─ прямой выход, при настройке — nfqws2
                                                   └─ блокировка
```

Схема показывает логическую связь, а не универсальный порядок всех hooks Netfilter. Для IP-правил обучение через DNS не требуется. Перечень hooks и поведение конкретного пакета зависят от backend и настроек.

Состояние ссылок и маршрутов отслеживается через Netlink и существующие механизмы сверки runtime. Проверка доступности удалённого адреса и наличие интерфейса — разные наблюдения: отрицательный ответ одного HTTP-сервиса сам по себе не доказывает, что весь туннель перестал работать.

Важная оговорка: transport-manager не владеет policy routing, но добавляет необходимые точечные разрешения `FORWARD` для управляемых TUN. Это не второй механизм выбора маршрута. Подробности — в [описании transport-manager](extensions/transport-manager/README.md).

## Маршрутизация и группы

### Правило отдельно от подключения

Подключение описывает путь выхода, список — назначения, а правило связывает условия с выходом. Одно подключение может обслуживать несколько списков; одна группа может объединять разные типы подключений.

Кроме доменов и IP/CIDR назначения, расширенный редактор позволяет задавать условия по источнику и портам. Поэтому можно, например, использовать IPv4-адрес конкретного телевизора как условие правила. Это не автоматическая политика по имени устройства: адрес нужно закрепить в DHCP, а IPv6 рассматривать отдельно.

Порядок правил важен. Человеческое имя не используется вместо устойчивого технического идентификатора в связях конфигурации. В интерфейсе видны зависимости: где подключение, группа, список или DNS-сервер используются другими объектами.

### Два способа выбора резерва

- **По задержке (`latency`).** Выбор рабочего выхода с учётом измерений и допуска; близкие результаты не обязательно вызывают переключение.
- **По приоритету (`priority`).** Предпочтительный выход используется, пока он работоспособен; после отказа выбирается резерв. Возврат на восстановившийся основной путь учитывает настроенную задержку возврата.

Поведение при недоступности маршрута задаётся отдельно: наследование настройки, блокировка или выбранный fallback. Это не одно и то же, что состояние процесса sing-box. [Модели API](docs/openapi.yaml) и [логика failure policy](src/config/route_failure_policy.hpp) описывают различие между `unknown`, ухудшенной проверкой и недоступным путём.

Переключение не гарантирует сохранение TCP/QUIC-сессии: смена внешнего IP может потребовать нового соединения со стороны приложения.

### Conntrack и совместимость с прошивкой

Марки соединений позволяют сохранить выбранный путь для следующих пакетов. Изменения должны учитывать маску собственных битов и не стирать чужие метки. Очистка устаревших соединений адресная: глобальный сброс conntrack не используется как обычный способ применения настройки.

Это особенно важно рядом с nfqws2, встроенными политиками Keenetic и аппаратным ускорением. Настройка выборочной видимости трафика при аппаратном ускорении не равнозначна отключению ускорения всей сети; её применимость зависит от подтверждённых возможностей прошивки и модели.

## Прокси, нативные подключения и подписки

### sing-box

Импорт ссылок охватывает **9 семейств**: VLESS, VMess, Trojan, Shadowsocks, Hysteria2, TUIC, AnyTLS, SOCKS и HTTP(S). `hy2://` и `hysteria2://` — варианты одного протокола, HTTP и HTTPS здесь считаются одним семейством. Наличие опции в ссылке не означает её поддержку любой версией sing-box: итоговый конфиг проверяет установленное ядро.

Поддерживаются импорт подходящего outbound JSON и параметры современных транспортов, включая REALITY там, где это допускает протокол и ядро. Это не обещание импорта произвольной полной конфигурации чужого клиента без преобразования её DNS и routing-семантики.

| Режим | Преимущество | Цена |
|---|---|---|
| `isolated`, по умолчанию | Отдельный процесс на управляемый прокси; ошибка одного процесса локализована | Больше процессов и расход памяти |
| `shared` | Один процесс обслуживает несколько отдельных TUN; меньше дублирующихся затрат | Его перезапуск или авария затрагивает все входящие в него прокси |

Перед заменой работающего общего конфига выполняется `sing-box check` кандидата. Ошибка проверки не требует остановки исправного процесса; при неудаче запуска предусмотрен возврат предыдущего конфига. Это не гарантирует бесшовное применение валидного изменения в `shared`: общей границы отказа у одного процесса избежать нельзя.

Менеджер использует ограниченный backoff для повторного запуска, а не бесконечные перезапуски без паузы. Недоступность одного внешнего тестового адреса не должна превращаться в рестарт всех исправных соседних подключений.

Адрес прокси-сервера нельзя направлять через этот же прокси. Панель предлагает создать исключение; это отдельное подтверждаемое действие, а не скрытое изменение правил при любом импорте.

### Штатные VPN Keenetic

Существующие VPN-интерфейсы обнаруживаются через API прошивки. Их можно использовать как выходы, не перенося реализацию туннеля в sing-box. Для поддерживаемых управляемых WG/AWG доступны импорт, редактирование, включение, выключение и удаление через панель.

Полный CRUD для всех протоколов прошивки не заявлен. В частности, OpenVPN и другие штатные подключения сначала настраиваются средствами KeeneticOS. Системные интерфейсы, входящие VPN-серверы и пользовательские импортированные клиенты имеют разные роли; список доступных выходов не даёт права удалять всё, что в нём обнаружено.

### Подписки

Подписка хранит источник, расписание и связи с выбранными для импорта подключениями. URI-списки, включая base64, обновляются фоново при закрытой панели. Новые узлы предлагаются пользователю; исчезнувшие не должны молча удалять его настройки.

Обновление параметров уже связанного узла не должно отменять пользовательское выключение этого узла. Срок действия и трафик показываются только при наличии соответствующих данных у провайдера. Обновление полной подписки sing-box JSON с `outbounds` этим механизмом пока не поддерживается.

Импорт имеет лимиты: размер загрузки подписки ограничен 1 MiB, план импорта — 512 записями. Это уже существующие ограничения входа, а не рекомендованное число одновременно работающих туннелей. Ресурсная ёмкость конкретного роутера требует измерений.

## Каталог и источники списков

Каталог входит в пакет, но содержимое внешних списков загружается из указанных источников. На 10.09.2026 в [файле каталога](packages/keenetic/keen-pbr/files/opt/usr/share/keen-pbr/catalog.json) **102 записи с уникальными ID**. Набор меняется вместе с исходниками; число не относится к количеству VPN-протоколов или правил в конфигурации пользователя.

Запись каталога может связывать домены, внешний rule-set и дополнительные IP/CIDR. Например, доменная часть и адресная часть сервиса решают разные задачи: DNS даёт динамические адреса доменов, явные подсети покрывают назначения, которые нельзя восстановить только по этим запросам.

Каталог имеет русские и английские названия/описания. Мастер связывает выбранное подключение, списки, правила и DNS, а не просто копирует домены в текстовое поле. Можно выбрать путь загрузки внешних списков; этот путь не следует путать с маршрутом пользовательского трафика из списка.

Поддерживаются:

- встроенные записи, URL и файлы на роутере;
- обычный текст с доменами и IP/CIDR;
- явно выбранный JSON-массив строк;
- явно выбранный YAML с блоком `payload`;
- совместимые бинарные `.srs`.

Нормализация приводит IP/CIDR к канонической форме, обнуляет host bits в подсетях и удаляет дубли. Для ошибочного JSON/YAML-импорта возвращаются номера строк и коды ошибок, а не молча принимается только удачный фрагмент. Формат сохраняется для следующих обновлений URL/файла.

JSON/YAML ограничены 2 MiB и 50 000 записями; превью показывает ограниченный фрагмент, но не сокращает сам импорт до размера превью. YAML anchors, произвольные объекты и команды правил Clash не интерпретируются как простые списки. Подробности и примеры — в [описании форматов](docs/list-source-formats.md).

## SRS без sing-box

Встроенный C++-декодер читает **SRS версий 1–5** и извлекает представимые доменные/IP-правила. Для этого не требуется ни работающий sing-box, ни его бинарник в роли декомпилятора.

Практический сценарий: Keenetic со штатным WireGuard/AWG использует готовые SRS-списки и policy routing, а sing-box вообще не установлен. Название `engines.singbox.ruleSets` в данных каталога описывает источник совместимого формата, а не необходимость запускать этот движок для каждого списка.

Границы преобразования важны:

| Вход SRS | Поведение |
|---|---|
| Представимые домены и доменные суффиксы | Перенос в доменные списки keen-pbr |
| Точный домен SRS | Семантика списка keen-pbr: сам домен **и поддомены**, а не exact-only |
| Суффикс только для поддоменов, не представимый этой семантикой | Пропуск, а не незаметное добавление корневого домена |
| Диапазоны IP назначения | Преобразование в покрытие CIDR |
| Regex, keyword, инверсия, дополнительные условия | Непредставимые части/правила пропускаются; сообщается о частичном импорте |
| Повреждённый контейнер, неизвестная версия, превышение лимитов | Ошибка декодирования, а не запуск внешнего декомпилятора |

Это **не полная реализация языка правил sing-box**. Сложные логические правила нельзя безопасно превратить в плоский список, просто выбросив дополнительные условия. Декодер сохраняет представимые альтернативы, но не должен расширять совпадение из-за удаления ограничивающего условия. Отдельно оговорённое преобразование exact-домена в root-and-subdomains — существующая семантика наших списков.

Встроены ограничения распаковки и структуры: до 16 MiB сжатого входа, 64 MiB распакованных данных, глубина логических правил до 32, отдельные пределы количества элементов и строк. Это верхние пределы декодера, не обещание комфортной работы списка такого размера на любом роутере.

Реализация: [декодер](src/lists/srs_decoder.cpp), [лимиты](src/lists/srs_decoder.hpp), [регрессионные тесты](tests/test_srs_decoder.cpp), [fuzz target](tests/fuzz/fuzz_srs_decoder.cpp). Монолитные Xray `geoip.dat` / `geosite.dat` не поддерживаются.

## nfqws2: что добавлено поверх обычного пакета

Сам обход выполняют **официальный nfqws2 и Lua-механизмы zapret2**. keen-pbr-sb добавляет интеграцию, подготовленные стратегии, исправления совместимости и наблюдаемость. Мы не называем чужой DPI-движок собственной разработкой.

### Пулы вместо одного общего перебора

В поддерживаемых профилях есть общие TCP, QUIC и UDP-пулы. Сбалансированный и максимальный профили дополнительно разделяют `googlevideo` TCP, YouTube TCP/QUIC и Discord UDP. Более специфические профили располагаются до общих. Для WebRTC/STUN предусмотрен отдельный passthrough без DPI-действий в соответствующем профиле.

Каждый ротатор имеет свой `key`: неудача в одном пуле не должна сдвигать выбор другого. Внутри используется штатный `circular()` с состоянием вида `autostate[pool_key][host_key]`, а не один глобальный переключатель стратегии для всей сети.

Ротатор перебирает подготовленные варианты по наблюдаемому обмену. Для TCP успех подтверждается данными сервера либо его ACK на действительно наблюдавшиеся отправленные данные: сама попытка загрузить большой запрос больше не считается успехом. Для UDP используется штатный детектор. Это не периодический запуск браузерного speedtest и не перезапуск всей службы при каждой неудаче.

В **максимальный** профиль встроен эксперимент для Discord: отдельные TLS-пулы для доменов приложения и `discord.media`, а для начального UDP-обмена сравниваются два фейка с одинаковым числом повторов. Ключи этих пулов не пересекаются с прежними; они не добавляют перехват всего UDP и не изменяют медиа-пакеты. Сбалансированный профиль сохраняет прежнее поведение. Ответ HTTP/TLS и первые ответные UDP-пакеты не доказывают успешный звонок; эксперимент не объявлен универсальным исправлением. [Границы и методика проверки](docs/NFQWS_DISCORD.ru.md).

Генератор согласует диапазоны обработки исходящих/ответных пакетов с работой детектора. Отдельно исправлена настоящая круговая ротация в десяти разобранных legacy QUIC/UDP-пулах; их исходный вариант сохранён первым кандидатом. Это не означает, что каждый старый пресет полностью переписан или одинаково удачен у всех провайдеров.

Общий TCP-пул и IP-ветвь MTProto наблюдают не только начало TLS, но и ответы сервера, RST и повторную передачу данных. При этом DPI-приёмы остаются ограничены началом соединения: наблюдение за ответом не означает отправку в ответный трафик фейков. Обычный HTTP сохраняет собственную обработку вне TCP-ротатора.

В **«Максимальном» `syndata` сохранён как экспериментальный последний, двенадцатый TCP-вариант**. Он вызывается на первом пустом исходящем SYN к порту 443, а не на уже пришедшем TLS ClientHello. Готовый SYN с данными клиента (TCP Fast Open) не переписывается. Неудачные повторные SYN учитываются: две неудачные сессии переводят штатный круг к следующему варианту. Уже зависшее соединение не становится исправным от смены варианта — приложению нужна новая попытка. Нет дополнительного процесса, очереди, перезапуска служб или глобального сброса соединений.

Для выбора профиля до появления SNI «Максимальный» использует штатный кэш имён nfqws2. **IP не равен домену:** на общем адресе CDN кэш содержит последнее увиденное имя, поэтому до появления настоящего SNI доменные исключения нельзя считать точными. Без подходящей записи в кэше доменный профиль не получает SYN; для обработки по адресам действуют соответствующие IP-списки. Обучение общего TCP-пула «Максимального» разделено по IP и порту сервера, чтобы результат SYN и последующего TLS относился к одному назначению. «Безопасный» и «Сбалансированный» не включают этот кэш или SYN-приём.

Для поддерживаемых «Сбалансированного» и «Максимального» профилей добавлено ограниченное **TCP-окно до 96 пакетов каждого направления**. Например, при штатном окне 1–15 собственные правила keen-pbr-sb добавляют только пакеты 16–96 в ту же очередь. Берутся действующие интерфейсы, порты и исключение уже обработанной метки nfqws2; UDP не расширяется. Дополнение не редактирует init-скрипт или бинарник nfqws2. Оно восстанавливается после запуска/перезапуска/обновления через панель, при загрузке роутера и событии штатного firewall. Если дополнение несовместимо с текущими правилами, обычный nfqws2 продолжает работать со своим окном. Нет отдельного постоянно работающего процесса или перезапуска маршрутизации.

На Keenetic важен не только текст правила: старый Entware `libxtables.so.10` неверно представлял `connndmmark` revision 1, теряя маску и инверсию. Пакет содержит небольшой [ABI-адаптер](src/keenetic/connndmmark_compat.c), который загружается **только нашим вспомогательным процессом** при подходящем контракте ядра/Entware. Системные библиотеки не заменяются, глобальный `LD_PRELOAD` не задаётся. При появлении штатной поддержки в Entware адаптер уступает ей; новые версии nfqws2 можно продолжать устанавливать.

В общих TCP-пулах исправлена изоляция fake-пакета от настоящего потока: положительный сдвиг sequence number дополнен неверной контрольной суммой (`badsum`). Один сдвиг сам по себе не гарантирует отбрасывание пакета сервером. Проверка включает настоящую приёмную TCP-сторону в изолированной сети и отдельную проверку на Keenetic; это не подмена аппаратной проверки Linux-тестом.

Это не обещание проходить любой тест TCP 16–20. Вне ограниченного окна обмен по-прежнему может быть невидим детектору. Короткий HTTP-ответ, исправный ротатор и успешная длительная передача — разные результаты; полный проход набора TCP 16–20 пока не подтверждён.

### Что сохраняется между перезапусками

Оперативный выбор ведётся для целей всех пулов, а не только YouTube или Discord; срок его хранения задаёт соответствующий ротатор. После перезапуска nfqws2 эта память не сохраняется целиком. В частности, GitHub и его сервер стилей — разные назначения, а общий TCP-пул «Максимального» различает IP и порт, не каждый домен на общем адресе CDN.

Постоянное сохранение ограничено тремя ревизируемыми пулами: `gv_tcp`, `yt_tcp`, `yt_quic`. Записывается **подтверждённый удачный слот**, связанный с пулом, ключом цели и ревизией matcher/detector/набора действий. Счётчики неудач и неподтверждённый новый кандидат на диск не переносятся.

- Ревизия меняется вместе со смыслом пула: старый номер слота не применяется к другому набору действий.
- Сохранение ограничено 64 записями и сроком 30 дней; записи выполняются с задержкой и ограничением частоты, а не на каждый пакет.
- Используются два проверяемых файла состояния. Ошибка чтения или сохранения этой подсказки не должна блокировать запуск nfqws2.
- Последний удачный вариант может не успеть записаться до внезапного отключения питания. Это не синхронный журнал каждого решения.

Отдельная телеметрия публикует сводки примерно раз в 10 секунд: распределение слотов, количество наблюдаемых целей и ожидающих неудач. Она не является полной трассировкой трафика. Сводка ограничена 64 пулами и 4096 целями; постоянный файл подсказок и агрегированная телеметрия — разные данные.

Источники: [генератор стратегий](build_scripts/build-nfqws-strategies.py), [Lua companion](packages/keenetic/keen-pbr/files/opt/usr/share/keen-pbr/nfqws-lua/rotator-telemetry.lua), [чтение состояния](src/util/nfqws_rotator_state.cpp).

### Обслуживание и совместимость

Панель позволяет выбирать и сохранять стратегии, редактировать конфигурацию, списки и Lua, просматривать и ограничивать журналы. Сохранение своей стратегии не равно её немедленному применению.

Перед применением проверяются конфигурация и необходимые файлы. При обновлении nfqws2 **через нашу панель** управляемые Lua-доработки восстанавливаются до запуска новой версии, а дополнительное TCP-окно — после запуска. Обновление напрямую через сторонний `opkg` или другой интерфейс не обещает тот же порядок восстановления. Для этой интеграции нужен IPK с соответствующими обработчиками: одна замена Lua или пресета не обновляет код уже установленного демона.

Предусмотрена совместимость с переписыванием TTL в Keenetic: соответствующая настройка сохраняет TTL обработанных nfqws2 пакетов, чтобы прошивка не разрушала смысл fake-пакетов. Это не универсальное правило для любого стороннего firewall.

Бинарные payload-файлы имеют [описание происхождения](packages/keenetic/keen-pbr/files/opt/usr/share/keen-pbr/nfqws-blobs/SOURCES.md) и контрольные суммы. Нельзя считать два разных имени blob двумя разными методами: некоторые распространённые payload побайтно совпадают.

### Ограничения диагностики и будущих экспериментов

Доменное исключение действует в контексте конкретного профиля и распознанного домена. Оно не является универсальным запретом обработки любого пакета к тому же IP. Диагностика теперь разбирает профили отдельно и показывает пересечения с IP-условиями; это не расшифровка каждого реального соединения и не доказательство полного исключения по одному совпавшему имени.

Отдельные Discord TLS/UDP-пулы в Max экспериментальные: успешное начало соединения не доказывает работу звонка. Настройки старого nfqws с `--dpi-desync` нельзя без проверки переносить в nfqws2 с Lua-стратегиями.

## DNS и границы доменной маршрутизации

Можно назначать DNS-серверы, задавать их порядок, привязки к доменам/спискам и путь, через который роутер обращается к выбранному серверу. Путь самого DNS-запроса и путь последующего соединения клиента — разные настройки.

Принудительный DNS помогает вернуть обычные запросы клиентов на порт 53 к роутеру. Ограничение DNS-over-TLS на 853 не превращает его в универсальный перехват DoH на HTTPS/443.

Отдельная отключаемая настройка Firefox использует canary `use-application-dns.net`. Она не управляет Secure DNS в Chrome, Edge или Яндекс Браузере и не отменяет вручную выбранный пользователем DoH. [Подробности и ссылки на документацию браузеров](docs/browser-secure-dns.md).

Важные ограничения:

- DoH/DoT, собственный VPN клиента и некоторые настройки ОС могут скрыть DNS от роутера.
- Несколько доменов могут иметь один CDN-IP. Маршрутизация по IP-набору не способна различить их после обучения только по одному DNS-ответу.
- WebRTC/P2P может использовать адреса вне доменных списков сервиса. Выборочный VPN не означает автоматическое отсутствие всех IP-утечек.
- IPv4 и IPv6 требуют согласованной настройки; успешная проверка только IPv4 не доказывает правильность IPv6.

Есть настройка сохранения изученных DNS-адресов при полном применении: она позволяет избежать ненужного холодного заполнения наборов. Это не массовый DNS-прогрев всех доменов и не способ устранить неоднозначность общих IP.

## Входящие VPN: домашние правила за пределами дома

Здесь речь о **VPN-серверах внутри Keenetic**, а не только об исходящих клиентах. Для поддерживаемых встроенных серверов можно определить, должны ли их клиенты проходить через правила keen-pbr-sb.

```text
Телефон вне дома
  → встроенный VPN-сервер Keenetic
  → DNS и правила keen-pbr-sb
  → прямой интернет / nfqws2 / выбранный исходящий VPN или группа
```

Механизм учитывает поддерживаемые WireGuard/AmneziaWG, OpenVPN, IKEv1/IKEv2, L2TP, SSTP и OpenConnect в зависимости от возможностей установленной прошивки. Один протокол не является «главным» для этой функции.

Реализация различает серверы со своим системным интерфейсом и сервисы с динамическими клиентскими интерфейсами/пулами. Используются актуальные данные KeeneticOS, а не зашитая подсеть для всех пользователей. Привязка VPN-сервера к LAN-мосту сама по себе не означает, что весь трафик этого моста принадлежит VPN-клиентам.

Для режима «через keen-pbr-sb» нужны согласованные DNS, маркировка, forwarding и обратный путь/SNAT. Только запись маршрута без возвратного трафика недостаточна. Для режима обхода наших правил сохраняется соответствующее прямое поведение, включая совместимость с nfqws2 там, где он настроен.

Ограничения: Keenetic должен быть доступен извне для выбранного входящего VPN; профиль клиента должен отправлять нужный интернет-трафик к домашнему роутеру. Сам сервис не выдаёт публичный IP и не устраняет CGNAT. Установка входящего сервера и компонента протокола остаётся задачей KeeneticOS.

Код: [обнаружение сервисов](src/keenetic/ndms_vpn_server_service.cpp), [разрешение клиентских политик](src/keenetic/internal_vpn_service_resolver.cpp), [динамические входящие интерфейсы](src/keenetic/internal_vpn_ingress_resolver.cpp).

## Экспериментальные функции

**Следующие механизмы экспериментальные. Они не гарантируют бесшовные звонки, отсутствие зависаний или автоматическое исправление любого сайта.**

- Переподключение старых соединений после изменения маршрута может помочь WhatsApp/Telegram перестать использовать прежний путь. Сам факт смены маршрута не гарантирует, что приложение сразу создаст новую сессию.
- Адресная попытка восстановления некоторых зависших WhatsApp-соединений опирается на идентичность штатного каталога Meta/WhatsApp. Поддержка ограничена соответствующим iptables-сценарием; общие адреса Meta могут затронуть простаивающее соединение другого приложения. Ограничения фоновой работы телефона этим не исправляются.
- Автоматический перевод в выбранный туннель доменов, с которыми не справился nfqws2, использует сравнение прямой и туннельной доступности. По умолчанию требуется также подтверждение по реестру блокировок; есть исключения и отдельный список результатов. Проверка с роутера не равна проверке браузера или звонка на клиенте.

Эти функции не являются основанием для общего сброса соединений или автоматической смены всех пользовательских правил.

## Наблюдаемость

На дашборде видны службы, используемые маршруты/группы, выбранные выходы, задержка и трафик интерфейсов. Локальные метрики роутера и кеши обновляются отдельно от тяжёлых запросов к KeeneticOS; события используются для адресного обновления данных.

Карточка проверки сайта связывает несколько вопросов:

1. Как разрешается адрес и дошёл ли DNS-запрос клиента до роутера?
2. Какие списки и правила совпали?
3. Какой путь ожидается и что видно в runtime?
4. Получен ли ответ с роутера/устройства, что известно о применимости nfqws2?
5. Есть ли адрес в реестре блокировок по данным внешней проверки, если пользователь её включил?

Подробная диагностика позволяет разбирать цепочку DNS → список → метка → маршрут → соединение. Проверка реестра обращается к внешнему сервису, которому становится известен проверяемый адрес. Ответ HTTP 403 доказывает получение HTTP-ответа, но не успешный вход на сайт или работу видеосвязи.

Раздел «Соединения» показывает активные соединения и ограниченную историю. Отображаемый домен — последнее известное соответствие DNS для IP, а не расшифровка TLS/SNI каждого соединения. [Описание раздела](docs/CONNECTIONS.ru.md).

Счётчики RX/TX и круговая диаграмма относятся к интерфейсам, а не к отдельным правилам. WAN и TUN могут учитывать разные уровни одного обмена. Доли на диаграмме не доказывают обход VPN; аппаратное ускорение и conntrack также ограничивают видимость отдельных счётчиков firewall.

Колокольчик показывает обновления, события подписок и диагностические сообщения. Если провайдер передаёт лимиты, доступны предупреждения об остатке и сроке действия. Очистка уведомлений синхронизируется между панелями; системный журнал этим не удаляется. Детали фоновых работ — в [диагностике задач](docs/background-task-diagnostics.md).

## WebUI, API и конфигурация

Мастер первого запуска связывает подключение, сайты и DNS; обычная настройка не требует редактировать JSON. CRUD-формы используют локальную сессию редактирования: изменение поля не должно само по себе создавать серверное применение до явного сохранения. Есть расширенный редактор, экспорт/импорт и отображение зависимостей объектов.

Панель поддерживает русский/английский, светлую/тёмную тему и мобильную компоновку. Типы backend и frontend генерируются из [OpenAPI](docs/openapi.yaml); структурированные коды и параметры ошибок отделены от текста перевода.

Внешний доступ к панели требует авторизации. Внутренний API transport-manager использует loopback и Bearer-аутентификацию. Ссылки подписок, outbound JSON, архивы и WG/AWG-конфиги могут содержать секреты; их нельзя публиковать вместе с диагностикой.

## Обновление и восстановление

Пакет проверяется по подписанному манифесту и хешам. Обновление keen-pbr-sb не означает автоматическую замену sing-box или nfqws2: у дополнительных компонентов свои действия обновления.

Конфигурация мигрируется между поддерживаемыми схемами. Для незавершённых операций предусмотрены записи восстановления и локальные резервные данные. Однако резерв конфигурации не заменяет резерв IPK, а резерв keen-pbr-sb — экспорт настроек KeeneticOS. Полная устойчивость к любому сбою питания/носителя не заявляется.

Подробности формата подписей — в [описании подписанных выпусков](docs/keenetic-release-signing.md). Сборки с одинаковым основным номером различаются по UTC-дате и времени исходного коммита. Alpha публикуется отдельными неизменяемыми тегами `alpha-<run_id>-<attempt>` с подписанным каналом `alpha`; публикация не меняет Stable/Latest. Номер ветки, имя канала, тег выпуска и версия IPK — связанные, но не взаимозаменяемые значения.

### Поведение панели при обновлении

В этой линии исправлено поведение обновления:

- Обычное обновление использует существующую авторизованную сессию панели без повторного запроса пароля перед установкой. Выдача архива с секретами, восстановление и откат остаются отдельными действиями; автоматическая локальная копия не требует скачивания пользователем.
- При перезапуске backend панель ожидает восстановление HTTP-связи и сверяет состояние той же операции, не отправляя установку повторно из-за `Failed to fetch`. После восстановления страницы наблюдение можно продолжить.

Это не обещание обновления без перерыва DNS/маршрутизации или бессрочного сохранения сессии входа после перезапуска backend. Готовность фиксируется выпуском и проверкой точного IPK, а не одной публикацией документации.

## Требования и платформы

- Keenetic/Netcraze с Entware в `/opt`, SSH-доступом к Entware и поддержкой policy routing.
- Компоненты KeeneticOS: **«Поддержка открытых пакетов»**, **«Модули ядра подсистемы Netfilter»**, **«Пакет расширений Xtables-addons для Netfilter»**.
- Для нативного VPN заранее установите его компонент в настройках прошивки: **WireGuard VPN** для WG/AWG, **OpenVPN** для `.ovpn` и соответствующие компоненты для остальных протоколов. keen-pbr-sb не устанавливает компоненты KeeneticOS за пользователя.
- Для AmneziaWG 2.0 нужна прошивка с его поддержкой: функция появилась в KeeneticOS 5.1 Alpha 3; ранней сборки 5.1 недостаточно. [Совместимость AWG](https://docs.amnezia.org/documentation/instructions/keenetic-os-awg/).
- Для доменных правил клиенты должны использовать управляемый DNS-путь роутера.

Полные Keenetic IPK собираются для `aarch64-3.10`, `mips-3.4`, `mipsel-3.4`. Наличие успешно собранного пакета не означает аппаратную проверку каждой модели: подтверждённые испытания на AArch64 нельзя автоматически переносить на MIPS/MIPSEL. Наличие вспомогательной цели сборки для другой архитектуры также не означает готовый поддерживаемый Keenetic IPK.

sing-box и nfqws2 опциональны. Базовый сценарий со штатным VPN и совместимыми SRS не требует ни одного из них. Объём памяти зависит от активных процессов, списков и трафика; рекомендации по десяткам туннелей без измерений не даются.

## Установка Alpha

**Alpha — тестовый канал. Workflow собирает три полных IPK: `aarch64-3.10`, `mips-3.4` и `mipsel-3.4`.** Перед установкой выполните требования выше, сохраните резервную копию keen-pbr-sb и экспорт KeeneticOS. Команды запускаются от `root` по SSH в Entware, не в командной строке KeeneticOS.

Новый Alpha-выпуск публикуется только после успешных проверок и сборки всех трёх пакетов: одна версия, один исходный коммит и отдельная проверка каждого пакета до подписи. Старые выпуски могли содержать только AArch64; их состав не меняется. Наличие IPK не подтверждает аппаратную приёмку на каждой модели. При отсутствии нужной архитектуры установщик не подменяет её другой архитектурой или каналом. Новые выпуски `next` больше не создаются, старые подписанные пакеты сохраняют свой формат проверки.

Последний опубликованный Alpha и его пакеты доступны в [Releases](https://github.com/blindtechnique/keen-pbr-sb/releases). Ориентируйтесь на выпуск с названием Alpha и нужной архитектурой; отметка Latest относится к Stable, а не к Alpha.

Команды ниже выбирают **последний опубликованный Alpha IPK** для вашей архитектуры и подходят для следующих обновлений без замены номера версии в команде. Установщик скачивается из ветки `alpha`; параметр `--alpha` выбирает тестовый канал, а не Stable/Latest. Переменная `KEEN_PBR_UPDATE_RELEASE_TAG=` снимает закрепление старого выпуска, если оно осталось в SSH-сессии. Установщик и временные файлы размещаются в `/tmp`, не занимая лишнее место в `/opt`.

Если новая [GitHub-сборка Alpha](https://github.com/blindtechnique/keen-pbr-sb/actions/workflows/release-keenetic.yml?query=branch%3Aalpha) ещё идёт, эти команды устанавливают предыдущий опубликованный Alpha. Дождитесь успешного завершения сборки и появления нового Alpha в Releases, если хотите установить именно новые изменения.

### Подготовка HTTPS

Перед первой установкой подготовьте загрузчик в Entware. Выберите **один** вариант — `wget` или `curl`; устанавливать оба не нужно.

Для **wget** установите поддержку HTTPS и сертификаты, затем удалите вариант без HTTPS. Выполняйте команды по одной: если `opkg update` или `opkg install` завершились ошибкой, остановитесь. Удаляйте `wget-nossl` только после успешной установки `wget-ssl`.

```sh
opkg update
opkg install ca-certificates wget-ssl
opkg remove wget-nossl
```

Если `wget-nossl` уже отсутствует, удалять нечего; сообщение об отсутствии этого пакета не мешает установке.

Для **curl** установите сам загрузчик и сертификаты; также выполняйте команды по очереди, продолжая только после успеха предыдущей:

```sh
opkg update
opkg install curl ca-certificates
```

Ошибка `wget: not an http or ftp url: https://...` возникает ещё до запуска установщика, если используемый `wget` не поддерживает HTTPS. Подготовка выше устанавливает загрузчик с поддержкой HTTPS; отключать проверку сертификатов или заменять HTTPS на HTTP не нужно. [Подробнее о HTTPS в Entware](https://github.com/Entware/Entware/wiki/Using-HTTPS-with-opkg).

### Первая установка

Через **wget**:

```sh
wget -O /tmp/keen-pbr-alpha-install.sh -T 30 https://raw.githubusercontent.com/blindtechnique/keen-pbr-sb/alpha/install.sh && TMPDIR=/tmp KEEN_PBR_INSTALL_LANGUAGE=ru KEEN_PBR_UPDATE_RELEASE_TAG= sh /tmp/keen-pbr-alpha-install.sh --alpha
```

Или через **curl**:

```sh
curl -fL --connect-timeout 30 -o /tmp/keen-pbr-alpha-install.sh https://raw.githubusercontent.com/blindtechnique/keen-pbr-sb/alpha/install.sh && TMPDIR=/tmp KEEN_PBR_INSTALL_LANGUAGE=ru KEEN_PBR_UPDATE_RELEASE_TAG= sh /tmp/keen-pbr-alpha-install.sh --alpha
```

### Обновление

**Если keen-pbr-sb уже установлен**, включая переход со Stable, добавьте `--update`. Если загрузчик ещё не подготовлен, сначала выполните подготовку HTTPS выше. Готовая команда через **wget**:

```sh
wget -O /tmp/keen-pbr-alpha-install.sh -T 30 https://raw.githubusercontent.com/blindtechnique/keen-pbr-sb/alpha/install.sh && TMPDIR=/tmp KEEN_PBR_INSTALL_LANGUAGE=ru KEEN_PBR_UPDATE_RELEASE_TAG= sh /tmp/keen-pbr-alpha-install.sh --alpha --update
```

Или через **curl**:

```sh
curl -fL --connect-timeout 30 -o /tmp/keen-pbr-alpha-install.sh https://raw.githubusercontent.com/blindtechnique/keen-pbr-sb/alpha/install.sh && TMPDIR=/tmp KEEN_PBR_INSTALL_LANGUAGE=ru KEEN_PBR_UPDATE_RELEASE_TAG= sh /tmp/keen-pbr-alpha-install.sh --alpha --update
```

Режим `--update` не запускает заново первичную настройку авторизации, DNS, sing-box и nfqws2. Во время установки панель и сетевые службы могут быть временно недоступны; не запускайте вторую установку, пока первая не завершилась.

Установщик выбирает самый новый alpha-тег по номеру запуска/попытки среди 100 последних публичных выпусков, затем фиксирует этот тег, проверяет архитектуру, SHA256 и подпись манифеста **именно канала alpha**. Если подходящего выпуска нет или проверка не пройдена, установка прекращается — скрытого перехода на Stable нет. HTTPS-проверку отключать не нужно; для wget требуется поддержка HTTPS и актуальные CA-сертификаты Entware.

**Выбор канала в новой WebUI:** «Настройки → Обслуживание → Канал обновления». Доступны Stable (main) и Alpha. Нажатие «Сохранить канал» меняет только выбор будущих обновлений: установленный пакет, VPN и DNS остаются прежними. Канал установленного пакета показан отдельно. Обычная установка наследует Stable, существующая Alpha — Alpha; явный выбор хранится в `/opt/etc/keen-pbr/update-channel`, не сбрасывается обновлением или пакетным откатом. Этот файл не является маркером сборки `/opt/usr/lib/keen-pbr/update-channel` и не заменяется пакетом.

Установка требует отдельного подтверждения точного тега и полной версии пакета. Если Stable старее установленной Alpha, панель объясняет отказ и не выполняет понижение: дождитесь нового выпуска или используйте проверенный пакетный откат вместе с его конфигурацией. При недоступности Alpha скрытого перехода на main нет; подпись, канал и архитектура по-прежнему проверяются. Если в старой панели выбора канала ещё нет, используйте SSH-команду выше с `--alpha --update`. Тег, точный source commit, IPK, установщик и подписи доступны в [Releases](https://github.com/blindtechnique/keen-pbr-sb/releases); исходники — в [ветке alpha](https://github.com/blindtechnique/keen-pbr-sb/tree/alpha).

## Разработка и проверки

Исходники ядра — C++17, transport-manager — Go, WebUI — TypeScript/React, целевые служебные скрипты — BusyBox `sh`, расширения nfqws2 — Lua. Python и Bun/Node используются инструментами разработки и сборки; это не набор постоянно работающих интерпретаторов на роутере.

Основные команды из корня репозитория, в подходящем Linux-окружении с зависимостями:

```sh
make
make test BUILD_JOBS=4
make transport-manager-test
make generate-check
make check-shell
make check-nfqws-assets
make check-nfqws-rotator-lua
```

Отдельные проверки frontend:

```sh
cd frontend
bun install --frozen-lockfile
bun run lint
bun run api:check
bun run i18n:check
bun run literals:check
bun test
bun run typecheck
bun run build
```

Изменения API требуют генерации backend/frontend-моделей, а не ручной правки generated-файлов. Для C++ есть sanitizer- и libFuzzer-цели; существующие fuzz-направления охватывают SRS, конфигурацию, списки, iptables и conntrack. Они не заменяют отдельный fuzzing Go-парсеров ссылок и аппаратную проверку runtime.

CI проверяет native/backend, frontend, Go, shell/package-сценарии и собирает целевые IPK. Точная конфигурация — в [workflow](.github/workflows/release-keenetic.yml), команды — в [Makefile](Makefile). Число тестов меняется: важны покрытые сценарии и результат конкретной сборки, а не обещание, что любое количество тестов исключает регрессии.

Изменения firewall, DNS, lifecycle или установки требуют приёмки точного собранного IPK на подходящем устройстве. Успешный frontend preview не проверяет эти части. Правила участия — в [CONTRIBUTING](CONTRIBUTING.md).
